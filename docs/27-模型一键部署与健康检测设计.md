## 27.1 目标与边界

买家在**自己的托管租约**里，从平台模型目录中选一个模型，平台先判断"这几张卡带不带得动"，带得动就一键拉权重、起推理服务，并持续给出健康状况。

| 做 | 不做（v1.2） |
|----|------------|
| 只部署在买家已租的卡上，属于买家私有资源 | 不对公网暴露推理端点（Q-43） |
| 只部署平台目录内、已在真机验证过的模型 | 买家上传自有权重 / 任意仓库地址（买家可在容器内自行部署） |
| 推理引擎只用 vLLM（按 digest 固定镜像） | SGLang / TensorRT-LLM 等其他引擎 |
| 每个租约同时最多 1 个部署 | 多模型同租约并行 |
| 仅 NVIDIA（随 `docs/25` 托管范围） | 国产卡 |

与 Token 工厂（`docs/05`）的边界：一键部署的模型是买家自用的私有服务，平台不接入 Token 工厂、不对外转售、不计 Token 费用（`docs/24` D-8）。

## 27.2 模型目录

由运营维护，买家只能从 `active` 条目中选择。**任何条目必须至少有一条真机验证记录才能上线**——不允许凭参数估算直接开放。

| 字段 | 说明 |
|------|------|
| `model_key` | 唯一键，如 `qwen3-32b-awq` |
| `source` / `repo` / `revision` | v1.2 只支持 ModelScope；`revision` 必须是固定提交号，不接受分支名 |
| `manifest` | 文件清单与每个文件的 sha256，拉取后逐一校验 |
| `weights_bytes` | 权重总字节数 |
| `quant` | `bf16` / `fp8` / `int4_awq` / `int4_gptq` 等 |
| `min_compute_capability` | 例：FP8 权重要求 ≥ 8.9（A100 为 8.0，不可用，需选 INT4 等变体） |
| `valid_tp` | 允许的张量并行度，如 `1,2,4,8`，由运营按注意力头数等结构确定 |
| `kv_bytes_per_token` | 全模型每 token KV 字节数（按引擎实际 KV 精度），由运营按结构计算并经真机核对 |
| `kv_replicated_across_tp` | KV 是否在各 TP 分片上复制（如 MLA 结构），影响容量计算 |
| `runtime_overhead_bytes` | 每卡固定开销（CUDA 上下文、激活、CUDA Graph），取真机实测值 |
| `max_model_len` / `min_context_tokens` | 模型上限与平台要求的最低可用上下文（默认 8192） |
| `engine_image` | vLLM 镜像 `ref@sha256`；`min_driver_version` |
| `engine_args` | 固定参数模板（白名单键） |
| `metrics_map` | 该引擎版本的 Prometheus 指标名映射（不同 vLLM 版本指标名不同） |
| `startup_timeout_s` | 启动超时，大模型可设 30 分钟 |
| `license` / `commercial_use` | 许可证与商用条件（`allowed` / `restricted` / `unknown`）；`restricted` 要求买家部署前单独确认 |

`gpu_catalog` 新增 `compute_capability`，供可行性判定使用；型号未填写该值时，该型号上的部署一律判为"无法判定"，不放行。

> **S5 实现口径（数值上限）**：为保证 27.3.1 的 int64 整数运算不溢出（溢出回绕曾导致除零 panic、超大模型被误判可行），目录录入时校验上限，超出即 40001：`weights_bytes` ≤ 4 TiB、`kv_bytes_per_token` ≤ 64 MiB、`runtime_overhead_bytes` ≤ 256 GiB、`max_model_len` ≤ 16,777,216、`valid_tp` 1–64、清单单文件 ≤ 1 TiB 且 ≤ 10000 个文件（总大小溢出检测累加，`weights_bytes` ≤ 清单总大小的规则不变）。判定函数自身也做溢出检测：库中旧行参数越界、租约单卡显存 ≤0 或 >1 TiB 时不报错、不 panic，判为不可行并在 M1 写明"无法判定"。

## 27.3 可行性判定

纯函数、确定性，不调用大模型。输入是**实时数据**（租约的卡、每卡显存与当前占用、驱动版本、节点缓存与磁盘），不是商品声明值。

### 27.3.1 显存与上下文

记：每卡显存 `V`，显存利用率上限 `u`（默认 0.90，买家可调 0.80–0.95），权重 `W`，每卡开销 `O`，每 token KV `K`，最低上下文 `Lmin`，租约卡数 `k`。

对 `valid_tp` 中每个 `tp ≤ k`：

```
每卡 KV 预算  B = V × u − W / tp − O
可容纳 token  T = B × tp / K          （KV 按 TP 切分）
              T = B / K                （kv_replicated_across_tp = true）
可行          B > 0 且 T ≥ Lmin
副本数        dp = floor(k / tp)
建议上下文    min(max_model_len, T 向下取整到 1024)
```

所有可行 `(tp, dp)` 组合都列给买家；默认推荐**用卡最多**的组合，同等用卡下取 `tp` 最小者（副本多、吞吐高）。示例：6 卡租约、模型 `valid_tp=1,2,4,8` → 可行组合可能是 `tp=2×dp=3`（6 卡全用）或 `tp=4×dp=1`（剩 2 卡），默认推荐前者。

示意（数值仅说明计算方式，实际以目录实测值为准）：某 32B 模型 BF16 权重约 65 GB、`K` 约 256 KB/token、`O` 取 4 GB：

| 租约 | tp | B（每卡） | T | 结论 |
|------|:--:|----------|---|------|
| 1 × 80 GB | 1 | 72 − 65 − 4 = 3 GB | 约 1.2 万 | 可行但上下文紧张，提示 |
| 2 × 80 GB | 2 | 72 − 32.5 − 4 = 35.5 GB | 约 29 万（再受 `max_model_len` 截断） | 推荐 |
| 2 × 24 GB | 2 | 21.6 − 32.5 − 4 < 0 | — | 不可行 |

### 27.3.2 其他检查

| # | 检查 | 结果 |
|---|------|------|
| F1 | GPU 架构 `compute_capability ≥ min_compute_capability` | 不满足 → 不可行，并提示目录中可用的其他量化变体 |
| F2 | 驱动 ≥ `min_driver_version` | 不满足 → 不可行（提示联系供给方升级） |
| F3 | 租约内各卡当前显存占用 ≤ 2% | 不满足 → 不可行，提示先停止占用显存的进程 |
| F4 | 节点已缓存，或模型缓存区剩余 ≥ `W × 1.1` | 不满足 → 不可行（可清理的 LRU 缓存计入可用空间） |
| F5 | 多卡 TP 且卡间无 NVLink（拓扑来自 `docs/25` P6） | 可行，提示性能会受 PCIe 带宽限制 |
| F6 | 卡健康（无 `faulty`、近 1h 无致命 Xid） | 不满足 → 不可行 |
| F7 | 许可证 `restricted` | 可行，需买家勾选确认后才能提交 |
| F8 | 租约卡型（`gpu_catalog` 型号）在该条目下没有 `result=pass` 的真机验证记录 | 可行，提示"未在该卡型实测，显存估算可能有偏差"；需买家勾选确认（提交字段 `untested_ack`，与 F7 的 `license_ack` 分开记录） |

判定结果连同计算明细写入部署记录（`feasibility` 字段），便于事后核对"当时为什么放行"。

## 27.4 部署流程

```
买家 POST 部署
  └─ 服务端重新做 27.3 判定（不信任前端结果）→ 写部署记录 pending → 入队 deploy_model
fleet worker
  ├─ checking  ：再次实时检查 F3/F4/F6（距提交可能已过去数分钟）
  ├─ pulling   ：节点缓存未就绪 → 入队/等待 pull_model（同节点同模型只拉一次）
  │               拉取容器写入 <cache>/<model_key>@<revision>.partial，逐文件 sha256 校验后原子改名
  ├─ starting  ：启动引擎容器（27.4.1），轮询 /health 直到成功或 startup_timeout_s
  └─ running   ：通过 L1–L3 首轮检查后进入；开始周期健康检测（27.5）
任一步失败 → failed，记录原因与引擎日志末尾 200 行（存部署记录，不含买家数据）
```

### 27.4.1 引擎容器

```
docker run -d --name omnis-d-<deploy_no> \
  --label omnis.lease=<lease_no> --label omnis.deploy=<deploy_no> \
  --gpus '"device=<租约内选定的 uuid…>"' \
  --network omnis-l-<lease_no>-net --network-alias omnis-engine \
  -v <cache>/<model_key>@<revision>:/model:ro \
  -p 127.0.0.1:<engine_port>:8000 \
  --shm-size 16g --restart no \
  <engine_image@sha256> \
  --model /model --served-model-name <model_key> \
  --tensor-parallel-size <tp> --data-parallel-size <dp> \
  --max-model-len <L> --gpu-memory-utilization <u> <目录模板参数…>
```

| 规则 | 说明 |
|------|------|
| GPU | 只能是该租约已分配的卡（`gpu_slots.lease_id` 校验），不能越出租约 |
| CPU / 内存 | 计入租约配额：两个容器**各自**用 `--cpus/--memory` 限制，二者之和不超过租约配额（默认引擎占一半，买家可调）。部署前先 `docker update` 缩减租约容器的配额；租约容器当前内存占用已超过缩减后的值时 `docker update` 会失败，此时部署失败并提示买家先释放内存。部署删除后把配额还给租约容器 |
| 端口 | 仅绑 `127.0.0.1`，从 `fleet.engine_port_range`（默认 41000–41999）分配，供平台经管理通道做健康检测；买家不经此端口访问。注意：宿主机上任何进程都能访问该端口，即供给方可以调用买家的引擎——与 `docs/24` §8「供给方物理接触数据」同属无法技术消除的风险，在使用规范中告知 |
| 参数 | 买家只可调 `tp/dp` 组合、`max_model_len`（≤ 判定建议值）、`u`；其余来自目录模板，白名单外的键一律拒绝 |
| 生命周期 | 随租约：包夜窗口结束时停止、窗口开始时自动恢复；租约到期/冻结/退款时停止；宽限期清除时随容器一起删除 |

### 27.4.2 买家访问

默认私有，不需要 API Key（只有租约内网络可达）：

```
# 在租约容器内
curl http://omnis-engine:8000/v1/models

# 在本地（经网关端口转发，docs/25 §25.6.1）
ssh -p 2222 -N -L 8000:omnis-engine:8000 l-7f3k9q2a@gw.omnisline.com
curl http://127.0.0.1:8000/v1/chat/completions …
```

### 27.4.3 权重缓存

| 规则 | 说明 |
|------|------|
| 位置 | 节点级目录（配置项，默认 `/data/omnis-models`），供给方接入时声明容量 `model_cache_gb`，探活核实 |
| 共享 | 同节点各租约共享，只读挂载；权重是公开模型，不含买家数据 |
| 归属 | 缓存占用不计入买家磁盘配额 |
| 淘汰 | 空间不足时按最近使用时间淘汰，**被运行中或启动中的部署引用的条目不可淘汰** |
| 校验 | 拉取完成逐文件 sha256；每次启动前校验目录完成标记与清单一致 |

## 27.5 健康检测

由 fleet 经管理通道在节点上执行（`docker inspect`、`curl 127.0.0.1:<engine_port>`、`nvidia-smi`），每 60s 一轮，结果写采样表。

### 27.5.1 检测分层

| 层 | 检测 | 方法 |
|----|------|------|
| L0 容器 | 是否运行、OOMKilled、退出码、重启次数 | `docker inspect` |
| L1 存活 | `/health` 返回 200 | curl，超时 5s |
| L2 就绪 | `/v1/models` 含 `served-model-name` | curl |
| L3 金丝雀 | 1 个 token 的补全请求，记录耗时 | `max_tokens=1`、`temperature=0`；默认开启，买家可关闭（关闭后 L3 不参与判定） |
| L4 指标 | 运行中/排队请求数、KV 缓存占用率、TTFT 分位、生成与预填充吞吐、抢占次数 | 解析 `/metrics`，指标名按目录 `metrics_map` 映射；分位由直方图桶增量计算 |
| L5 硬件 | 所用卡温度、功耗、降频原因、ECC、Xid | `nvidia-smi`，与 `docs/25` 周期探活共用 |

**不以显存占用率判断健康**：vLLM 启动即按 `u` 预分配显存，显存长期 90% 是正常状态。容量是否吃紧看 KV 缓存占用率和排队数。

### 27.5.2 健康判定

| 状态 | 条件（任一满足） |
|------|----------------|
| `unhealthy` | 容器未运行或 OOMKilled；L1 连续 3 次失败；L3 连续 3 次失败；所用卡出现致命 Xid / 不可纠正 ECC |
| `degraded`（持续 5 分钟） | 排队 > 0 且 KV 占用 ≥ 95%（容量饱和）；抢占次数增长；TTFT P95 > 基线 3 倍（基线为 running 后首小时金丝雀中位数）；所用卡温度 ≥ 85°C 或出现温度/功耗降频；可纠正 ECC 持续增长；近 1 小时内发生过自动重启 |
| `healthy` | 其余 |

每次判定给出 `health_reason`（机器可读代码 + 中文说明），例如 `capacity_saturated`：「请求排队且 KV 缓存已满，建议降低并发、缩短上下文或增加卡数」。

### 27.5.3 自动处置

| 情况 | 处置 |
|------|------|
| 容器退出 / OOM / L1 连续失败 | 自动重启，退避 1 / 5 / 15 分钟；滚动 1 小时内最多 3 次；超过 → `failed`，通知买家，附引擎日志末尾 |
| 致命 Xid / 不可纠正 ECC | **不重启**；卡标 `faulty`，按 `docs/25` 资源异常处理并通知三方 |
| `degraded` | 只通知，同一原因 30 分钟内最多 1 次 |
| 平台无法连接节点 | 健康标为 `unknown`，不推断为故障；节点层面按 `docs/25` 处理 |

### 27.5.4 采样与展示

采样表保存 7 天，每日清理。查询接口按时间范围降采样：1h → 60s 原始点，24h → 5 分钟均值，7d → 1 小时均值。买家页面展示：当前状态与原因、TTFT、吞吐、排队、KV 占用、卡温度曲线，以及重启记录。

## 27.6 状态机

```
pending → checking → pulling → starting → running ⇄ restarting
   │         │          │          │         │
   └─────────┴──────────┴──────────┴─────────┴──► failed
                                             │
               包夜窗口结束 / 买家停止 / 租约到期 ─► stopping → stopped
               包夜窗口开始（auto_resume=1）     ◄── stopped ──► starting
```

`health`（`unknown/healthy/degraded/unhealthy`）只在 `running/restarting` 时有意义，与上面的生命周期状态分开存储。迁移全部守卫式更新。
