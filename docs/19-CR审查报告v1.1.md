## 3. 资金与数量安全专项审查

### 3.1 ValidateOrderParams / validateOrderParams

**结论：已确认到位**

- `service.go:414–416`：`quantity < minOrder` 拦截负数量和零数量（负数量会被 `< minOrder` 的默认 minOrder=1 捕获）
- `service.go:417–419`：数量上限 `MaxOrderQuantity=100000`
- `service.go:420–422`：库存校验 `p.Stock > 0 && checkStock && quantity > p.Stock`
- `service.go:425–427`：买断 `PricingPerpetual` 强制 `duration=1`，忽略客户端传值（防止被时长放大总价）
- `service.go:429–436`：最小租期 + 最大时长上限 `MaxOrderDuration=87600`
- `service.go:404–407`：面议 `price_negotiable` 和 `colocation` 双重拦截禁止下单
- `service.go:408–410`：`UnitPrice <= 0` 拒绝下单

**一处分歧**：`MaxOrderDuration=87600` 注释说"约10年(小时)"，但对 monthly 计费模式，duration 语义上是月份数而非小时数，87600 个月 ≈ 7300 年，远超出合理范围。不过 `CalcOrderAmount` 的总金额上限 `MaxOrderTotalFen` 会在金额侧兜底拦截。**建议**：按 pricing_mode 动态设置上限而非统一 87600。

**注意**：`p.Stock = 0` 时库存校验分支被跳过（`p.Stock > 0` 才进入），意味着 Stock=0 被视为"不限库存"。需业务确认这是设计意图还是字段语义需要澄清（见开放问题 Q-CR-01）。

### 3.2 CalcOrderAmount（int64 分，溢出保护）

**结论：已确认到位**

- `service.go:442–444`：入口三元校验（unitPrice > 0, quantity > 0, duration > 0）
- `service.go:449–450`：`step := unitPriceFen * qty; if step/unitPriceFen != qty` 标准溢出检测
- `service.go:451–452`：`total := step * d; if total/step != d` 二次溢出检测
- `service.go:453`：`total <= 0` 兜底
- `service.go:454–456`：总额上限 `MaxOrderTotalFen = 1e12`（100亿元）
- `service.go:458–460`：佣金分步计算 `total/10000*rate + (total%10000)*rate/10000`
- `service.go:461`：`fee < 0 || fee > total` 异常兜底

**佣金公式验证**：`service_test.go:293–303` 对 `rate ∈ {0,1,250,500,1000}` 和 `total ∈ {1,7,333,9999,10000,10001,123457,999999999}` 的所有组合验证分步公式等于朴素公式 `total*rate/10000`，**全部通过**。

**单价单位与时长语义的矛盾**（标注为 P1-1）：代码中 `Duration` 字段注释为"小时"，且 `MaxOrderDuration` 注释为"约10年(小时)"。但对于 `daily` 计费模式，单价是"元/卡·天"（如 wireframe line 401 所示 4800/卡·天），此时 duration=1 应表示 1 天（24 小时），而非 1 小时。在 `hourly` 模式下 duration=24 表示 24 小时，但在 `daily` 模式下 duration=24 会被 calc 当成 24 天而非 24 小时。**如果前端按小时数传 duration，daily 产品会被严重多收费**；如果前端按"几个计费周期"传 duration，则 `MaxOrderDuration=87600` 缺乏意义且 Order DDL 的 `COMMENT '租期(小时)'` 是错的。详见问题清单 P1-1。

### 3.3 PlaceOrder（库存扣减原子性、TOCTOU）

**结论：有缺陷（P1-2）**

- `service.go:466`：`GetProductByID` **在事务外**读取产品数据（价格、库存、状态等）
- `service.go:492`：开启事务 `Beginx()`
- `service.go:496`：事务内 `DecrProductStock(tx, id, qty)`
- `repository.go:239`：`UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?`

**TOCTOU 窗口**：产品数据在事务外读取，到事务内扣库存之间可能被另一并发请求修改价格、库存或状态。`ValidateOrderParams` 读到的 `p.Stock=10` 和 `p.UnitPrice=3500` 可能已过期。

**防护程度评估**：
- 库存超卖：`WHERE stock >= ?` 阻止了实际超卖（乐观锁模式），多数情况下安全
- 价格变更：如果供给方在用户下单与库存扣减之间改了价格，用户会按旧价格下单。这是产品策略问题，非安全漏洞
- 状态变更：`service.go:468` 事务外检查 `p.Status != "active"`，到事务内扣库存时状态可能已变

**建议**：将 `GetProductByID` 移入事务，或使用 `SELECT ... FOR UPDATE` 在事务内读（如 `SyncResource` 已实现的那样），确保订单创建基于产品的当前真实状态。

### 3.4 RenewOrder / ValidateRenewParams

**结论：已确认到位，有一处旁路风险（P1-3）**

- `service.go:874–911`：`RenewOrder` 校验买家身份（line 878）、订单状态（line 879）、禁止买断续租（line 884）
- `service.go:889`：调用 `ValidateRenewParams`，参数 `checkStock=false`
- `service.go:397–398`：续租不校验库存的语义正确（买家已持有这批卡，续租只是延长期限）
- `service.go:910`：`CreateOrderTx(nil, ...)` — 续租订单**不进入事务**（tx 传 nil），也没有走 PlaceOrder 的事务路径，因此续租订单的创建是**非事务性的**。这本身不算资金漏洞（续租不扣库存），但如果有退款逻辑需关联原订单，缺少事务保护可能产生不一致。

**防线分析**：续租不开事务、不扣库存、仅创建新续租订单，逻辑自洽。但需确认退租/退款场景下如何处理——如果原单退了但续租单还在 active，就是业务状态不一致。

### 3.5 SyncResource（C-05 盘点安全）

**结论：已确认到位**

- `service.go:816`：`stock_after >= 0` 拒绝负数
- `service.go:822`：开启事务
- `service.go:827`：`LockProductForUpdate(tx, id)` — `SELECT ... FOR UPDATE` 行锁
- `service.go:831–833`：归属校验（非运营时必须是商品所属供给方）
- `service.go:835–839`：主动盘仅限运营 / 被动报仅限供给方 —— **身份与类型不会错配**
- `service.go:849`：快照写入同一事务
- `service.go:851`：库存更新同一事务
- `service.go:852`：提交

**`FOR UPDATE` 行锁**在 InnoDB 中阻止并发盘点同一商品的写冲突，确保 `stock_before` 是可信基线。设计与 `PlaceOrder` 形成对比——`PlaceOrder` 没做到这点。

### 3.6 ComputeAnomaly（整数比值判定）

**结论：已确认到位**

- `service.go:793–801`：`abs*anomalyRatioDen > stockBefore*anomalyRatioNum`，即 `abs*10 > before*3`
- 等式 `abs/before > 3/10` <=> `abs*10 > before*3`，使用**严格大于**，所以恰好 30% 不算异常
- 测试 `service_test.go:367–369` 已验证：`stock_before=100, stock_after=70` 差 -30 不算异常，-31 算
- `stock_before <= 0` 时不判异常（无基线，合理）
- 测试覆盖小基数（2→1，差 50% 判异常）和大基数（100000→99999，差 0.001% 不判异常）

**注意**：`stock_before <= 0` 既不判异常也无错误返回，静默通过。如果供给方把库存从 0 改为一个很大的数（可能是数据修正而非异常），不会标记 anomaly。业务上可能合理，但建议确认。

## 4. 问题清单

### P0（阻断上线 / 资金风险）

**P0-1 | `ConfirmDelivery` 无买家身份校验**
- **位置**：`compute/service.go:696–702` 定义，`compute/handler.go:295–299` 调用
- **影响**：任意认证买家可激活任意 paid/provisioning 订单并获取访问凭证，属于严重越权
- **建议**：在 `ConfirmDelivery` 开头加入 `if o.BuyerID != buyerID { return fmt.Errorf("无权操作") }`（需新增 `buyerID` 入参）

**P0-2 | 支付回调无签名验证，Mock 接口直接放行**
- **位置**：`payment/service.go:49–57` `HandleCallback` 未调用签名验证；`payment/repository.go:155–157` `VerifyCallback` 硬编码返回 `false`
- **影响**：任何知道 order_no 的人可通过未鉴权的 `/api/v1/payment/callback` 伪造支付成功。虽然平台当前使用 mock 支付，但这条铁律明确禁止生产代码做假实现：未接入的外部依赖必须返回错误，而不是假装成功。
- **建议**：
  1. `HandleCallback` 在更新支付状态之前调用 `VerifyCallback()`
  2. `VerifyCallback` 返回明确的 `ErrYeepayNotConfigured`（与 `CreatePayment` 一致），而不是 `false`
  3. 或者如果这是 v1 阶段无真实支付的已知设计，则 `HandleCallback` 直接 `return ErrYeepayNotConfigured`，禁止处理任何回调

**P0-3 | 盘点异常标记无告警接线**
- **位置**：`compute/service.go:842–848` — `anomaly` 被写入 `resource_snapshots` 表
- **影响**：C-05 需求明确要求"标记 anomaly → 触发风控告警"，当前 anomaly 只是数据库里一个 TINYINT 字段，没有任何告警动作（无日志、无 webhook、无 status 变更）
- **建议**：至少加一条 `slog.Warn("resource anomaly detected", ...)` 并创建 TOD 对应风控模块升级

**P0-4 | `FreezeOrder` 不吊销凭证**
- **位置**：`compute/service.go:567–569`
- **影响**：冻结订单后买家的访问凭证仍然有效，可继续访问算力中心。冻结通常意味着风控/违规，应按 C-06 安全要求"订单冻结 → 凭证自动失效"
- **建议**：`FreezeOrder` 末尾加 `s.revokeAccessByOrderNo(orderNo)`

**P0-5 | `RevokeExpiredAccess` 无定时调度**
- **位置**：`compute/service.go:773–776` 函数定义；`compute/repository.go:492–499` SQL

| `daily` | 天数 | 元/卡·天 | 3650（10 年） |
| `weekly` | 周数 | 元/卡·周 | 520（10 年） |
| `monthly` | 月数 | 元/卡·月 | 120（10 年） |
| `perpetual` | 强制 1 | 元/台（买断） | 1 |

选此方案的原因：前后端只传一个数字，`CalcOrderAmount` 保持 `单价 × 数量 × 周期数` 的纯乘法，**不引入除不尽的取整误差**——涉及资金，取整规则越少越安全。

### 改动点

**修复前的实际后果**（两处，均已消除）：
1. `monthly` 订单的 `lease_end_at` 会被算成「下单后 N 小时」——买 1 个月的算力，租期几小时后就到期。
2. 同一订单的**访问凭证也在几小时后失效**（`access_expires_at` 同样按小时算），买家拿到凭证就用不了。
