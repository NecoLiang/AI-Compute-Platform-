## 25.1 问题与目标

现状（C-06 人工交付）的断点：

1. 上架时不采集任何登录信息、不做探活，商品"可售"不代表机器可用。
2. 买家付款后要等供给方手工回填 IP / 账号 / 密码，平台无法验证凭证真实可登录（Q-24 至今未定）。
3. 到期"吊销"只吊销了平台自己生成的 key/value；买家手里的真实 SSH 密码仍可登录，到期不续费也停不下来（Issue #8）。

目标：

| # | 目标 | 验收口径 |
|---|------|---------|
| G1 | 上架前证明机器"可登录、卡型卡数属实、端口未裸露" | 探活报告全部必检项通过才允许提交审核 |
| G2 | 付费成功即生效，无需供给方在线、无需买家签收 | 支付成功 → 可登录，P95 ≤ 2 分钟（基础镜像接入时已预拉取）；开通耗时不计入租期 |
| G3 | 买家只通过平台网关登录，拿不到机器真实地址与供给方凭证 | 买家侧只出现 `gw.omnisline.com` 与租约登录名 |
| G4 | 到期不续费即无法连接 | 租期结束后 ≤ 90 秒新连接被拒、已有会话被切断 |
| G5 | 宽限期内续租可恢复原环境；宽限期后数据清除并留回执 | 清除回执写审计日志 |

非目标（v1.2 不做）：跨节点迁移租约、NAT 后无公网节点、国产卡托管、买家自定义镜像、会话内容录屏。对应开放问题见 `docs/24`。

## 25.2 两种履约模式

商品新增 `fulfillment_mode`：

| 模式 | 适用 | 交付 | 到期 | 说明 |
|------|------|------|------|------|
| `manual` | 全部类型（存量默认） | C-06 原流程：供给方回填凭证、买家签收 | 吊销平台凭证（现状） | 不变，保持兼容 |
| `managed` | 仅 `card_rental` | 平台自动开通租约容器/账户，经网关登录 | 网关拒绝 + 节点侧停机 | 本文设计对象 |

托管模式的交付形态沿用商品现有字段 `delivery_mode`（托管只接受 `container` / `bare_metal`，`vm` / `rack` 只能人工交付），同一商品下的节点形态一致：

| delivery_mode | 买家拿到 | 可分卡 | 到期可否由平台保证回收 |
|---------------|---------|:--:|------|
| `container`（默认，推荐） | 独立容器，容器内 root，独占指定 GPU | 是 | **能**：容器停止即断开，数据卷可删除 |
| `bare_metal` | 整机账户（含 sudo） | 否，只能整机 | **不能完全保证**：买家有 root 可留后门，需供给方重装确认后才能再售（§25.7.4） |

> **S1/S2 实现口径（商品与下单契约）**：`managed` 商品创建即 `draft`（人工为 `pending`），`stock` 忽略并写 0；经 `PUT /supplier/products/:id` 提交审核时须至少一台 `verified` 且型号一致的托管节点（不满足 40001 并逐节点列出原因），审核通过前复核一次；`fulfillment_mode` 创建后不可改（40001）；`fleet.enabled=false` 时可建草稿但提审/下单 40001。下单错误：fleet 未启用 40001、租约钩子未接入 50000、买断计费 40001、无整机余量 40900、整机交付未接入（T-089）50000。完整契约见 `docs/api/compute-api.md`「托管商品」「托管订单」。

## 25.3 总体架构

```
 买家终端                                平台                                 供给方节点
 ───────                ┌──────────────────────────────────┐          ─────────────────────
 ssh -p 2222            │ 访问网关主机 (新增, 按流量计费)    │          sshd(管理口, 仅放行控制面IP)
 l-7f3k9q2a@gw...  ───► │  sshpiperd + omnis 路由插件        │ ──────►  租约端口 40000-40099
                        │  cmd/accessgw                      │  (仅放行  └─ 租约容器 sshd:22
                        └──────────┬───────────────────────┘   网关IP)     (--gpus device=UUID…)
                                   │ HTTPS + HMAC
                                   │ /internal/accessgw/*
                        ┌──────────▼───────────────────────┐
                        │ 主服务 (现有单体, 123.56.177.241) │  SSH(平台管理密钥)
                        │  internal/compute  订单/库存/续租   │ ───────────────────────► 管理口
                        │  internal/fleet    节点接入/探活/   │   docker / nvidia-smi
                        │                    任务队列/租约    │
                        │  internal/scheduler (docs/23)      │
                        │  MySQL / Redis (仅 127.0.0.1)      │
                        └──────────────────────────────────┘
```

关键取舍：

| 决策 | 选择 | 理由 |
|------|------|------|
| 节点侧是否装常驻 agent | **不装**，平台经 SSH 无 agent 管理 | 供给方只需开一个 SSH 账户，零安装；docs/23 的推送心跳保留为可选 |
| 网关是否自研 | **用 sshpiper（MIT）+ 自写路由插件** | 遵循 docs/16「不自研框架」；完整 SSH 协议透传，端口转发 / sftp / scp 均可用 |
| 网关是否并入主服务进程 | **独立进程、独立主机** | 主服务只监听 127.0.0.1、防火墙只放 ssh（docs/21）；买家流量与带宽计费不应压在主机上；网关被打不影响交易 |
| 网关是否持有业务数据 | **不持有**，鉴权与路由每次问主服务（带短缓存） | 网关无数据库连接，泄露面最小；不构成"微服务"——没有自己的库和领域逻辑 |
| 平台管理通道与买家通道 | **分离**：管理走节点 sshd，买家走租约端口 | 网关主机即使被攻破，也拿不到能控制节点的管理密钥 |

`internal/fleet` 是单体内新包，遵守 docs/16 模块规则：只通过 `compute` 暴露的 Service 方法改订单/库存状态，不直接访问 `compute` 的 repository。

**表归属与跨模块事务**（docs/16「每张表只归一个 repository」）：

| 归属 | 表 |
|------|----|
| `fleet` | `gpu_slots`、`node_probe_reports`、`node_tasks`、`leases`、`buyer_ssh_keys`、`access_sessions`、`lease_outages`；`supplier_nodes` 的托管列（026 新增列）由 fleet 写，其余列仍归 `scheduler` |
| `compute` | `orders`、`products`、`order_deliveries`、`order_renewals`（含新增 `fulfillment_mode`、`settle_ready_at`） |
| `payment` | `payments`、`settlements`、`payment_refunds`（新增，见 25.7.6） |

订单状态流转仍由 `compute` 的私有事务完成（`releaseStockTxDeadline`、`ApplyRenewalPaymentTx` 等），fleet 不能另开事务插入。做法与现有 `payment.SetRefundHook` 一致——`compute` 暴露注入点，由 `main` 在启动时把 fleet 的实现注入：

```go
// compute 包
type LeaseHooks struct {
    OnPaidTx  func(tx *sqlx.Tx, order *Order) error             // 支付确认事务内: 租约 reserved→pending, 入队 provision
    ReleaseTx func(tx *sqlx.Tx, order *Order, reason string) error // 关单/退款/到期事务内: 释放卡槽/预订, 租约迁移, 入队 stop/purge
    RenewTx   func(tx *sqlx.Tx, parent, renewal *Order) error    // 续租下单与支付事务内: 预留/顺延
}
func (s *Service) SetLeaseHooks(h LeaseHooks)
```

`fulfillment_mode=managed` 的订单在上述事务点调用对应钩子；`manual` 订单不调用，行为不变。钩子未注入而出现托管订单时返回 50000（「托管履约模块未启用」），不静默跳过。

> sshpiper 插件与 sshpiperd 之间通过标准输入输出上的 gRPC 通信。业务负责人 2026-10-28 确认：**第三方组件必需的 gRPC 可以接受**（docs/16 §9 已同步注明）；业务模块之间仍走进程内函数调用。

**网关主机部署（Q-32 已定）**：网关主机即运行 `cmd/accessgw` 的那台服务器——买家所有 SSH 连接（含 scp/sftp 传数据、端口转发）都经它中转到供给方节点。部署在**阿里云北京**，与主服务 `123.56.177.241` 同地域同 VPC：调主服务内部接口走内网，不占公网带宽；独立一台（起步 2 核 4G、按流量计费、固定公网 IP 供节点白名单），不与主服务混部，避免买家大流量挤占交易站点带宽。

## 25.4 节点接入（上架前）

### 25.4.1 供给方前置条件（上架规范 v2 列明，探活逐项校验）

| 项 | 要求 |
|----|------|
| 系统 | Linux x86_64，systemd；NVIDIA 驱动 ≥ 平台配置的最低版本 |
| 容器 | Docker ≥ 24 + nvidia-container-toolkit，`docker run --gpus` 可用 |
| 管理账户 | 一个可执行 `docker` 的账户（docker 组或 root）。**不要求 sudo**；须告知供给方 docker 组权限等同 root |
| 网络 | 管理 SSH 端口对平台控制面 IP 可达；租约端口段（默认 40000-40099，可改）**只**对网关出口 IP 开放 |
| 磁盘 | 每卡可分配数据盘 ≥ `disk_per_card_gb`（供给方填写，探活核实）；模型缓存区见 `docs/27` |
| 磁盘配额 | 分卡出租要求 Docker 数据目录在 xfs+pquota 上（`--storage-opt size=` 可用）；不满足则该节点只能整机出租 |

### 25.4.2 接入流程

```
供给方                         平台
  │ ① 新建商品草稿(fulfillment_mode=managed)
  │ ② 添加节点 POST /supplier/nodes [expected_host_fingerprint 推荐]
  │                                                     生成该节点专属 ed25519 管理密钥对
  │                                                     私钥 AES-256-GCM 加密入库
  │ ③ GET /supplier/nodes/:id/onboarding  ◄──────────  返回: 公钥行(带 from="控制面IP" 限制)
  │                                                     + 租约端口放行脚本(按发行版生成)
  │ ④ 二选一:
  │   a. 自行把公钥加入 authorized_keys (推荐, 平台不接触密码)
  │   b. 提交一次性密码, 平台用它登录一次写入公钥后立即丢弃
  │      (须同时提供预期指纹, 否则首次握手无从校验, 见下方 S1 口径)
  │ ⑤ PUT /supplier/nodes/:id/ssh  {host,port,user[,bootstrap_password][,expected_host_fingerprint]}
  │ ⑥ POST /supplier/nodes/:id/verify   ─────────────► 入队 probe 任务
  │                                                     首次连接记录主机指纹(待确认)
  │ ⑦ 页面展示指纹, 供给方在机器上执行
  │    ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub 比对
  │    POST /supplier/nodes/:id/host-key/confirm ────► 指纹钉死; 继续完整探活
  │ ⑧ 查看探活报告, 全部必检项通过 → 商品可提交审核
```

要点：

- **密码只用一次、不落库、不进日志**：仅在 ⑤ 的请求处理内存中使用；写审计 `node.bootstrap_password_used`（不含密码）。登录失败直接返回错误，不重试、不缓存。
- **主机指纹钉死**：之后每次连接校验指纹；不一致 → 节点 `verify_status=key_mismatch`，立即停止新分配并通知供给方与运营。重装系统后由供给方重新走 ⑦ 确认，并写审计。
- **同一台物理机不能重复上架**：`gpu_slots.gpu_uuid` 全局唯一；主机指纹经 `host_fp_claim`（验证通过时 = 指纹，删除/重置时置 NULL）唯一约束保证在 `verified` 节点间唯一，冲突即拒绝并提示。若真实机主发现卡 UUID 或指纹已被他人抢先登记，走运营仲裁（工单），运营核实后可将对方节点置 `suspended` 并释放占用。
- 管理密钥按节点生成，单个节点泄露不影响其他节点；节点删除时密钥作废。
- **删除节点**：现有 `DELETE /supplier/nodes/:id` 为硬删除。托管节点存在非 `free/withheld` 卡槽时返回 40900「节点上有进行中的租约」；否则同一事务内删除其卡槽、清空 `host_fp_claim` 再删节点，并重算商品派生库存。

> **S1 实现口径（T-077/T-080，与上文差异）**
> - 删除判定为「存在 `reserved/leased/draining` 卡槽或任何绑定了 `lease_id` 的卡槽」才 40900；无租约的 `faulty` 卡槽允许随节点删除。删除时同时作废该节点 pending/running 的任务。`fleet.enabled=false` 时删除托管节点返回 50000（无法安全清理卡槽），新增 ssh 节点返回 40001。
> - **目标地址策略（SSRF 防护，CR-S1 M2）**：平台主动连接供给方地址（管理 SSH、P11/P12、开通自检、网关上游）一律经同一拒绝名单（`backend/pkg/netguard`）：内置 `0.0.0.0/8`、`10/8`、`100.64/10`（CGNAT，含阿里云元数据 `100.100.100.200`）、`127/8`、`169.254/16`（含 `169.254.169.254`）、`172.16/12`、`192.168/16`、`192.0.0.0/24`、TEST-NET、`198.18/15`、`224/4`、`240/4`、`::/128`、`::1`、NAT64 `64:ff9b::/96`、`64:ff9b:1::/48`、`100::/64`、`2001:db8::/32`、6to4 `2002::/16`、`fc00::/7`（ULA）、`fe80::/10`、`fec0::/10`、`ff00::/8`；IPv4-mapped IPv6 按 IPv4 判。平台自身 VPC/内网段、主服务与网关公网段经 **`fleet.deny_cidrs`** 追加（只能追加，不能放行内置段；无任何生产放行开关）。
>   - **提交时**（`PUT /ssh`）：IP 字面量直接判；域名当场解析（5s），**任一**解析结果命中即拒绝，无法解析也拒绝；均返回 40001 通用提示（「host 不允许…」/「host 无法解析…」），不回显解析出的地址，`localhost` 照旧拒绝。
>   - **拨号时**：`net.Dialer.Control` 钩子按实际连接地址再判一次（覆盖 DNS rebinding）。
>   - **网关**：主服务在 `/internal/accessgw/auth` 中把节点 host 按同一策略解析为**IP 字面量**再下发给网关（sshpiperd 上游拨号无法挂钩子，由此防 rebinding），命中拒绝名单时该次鉴权返回 50000（网关拒绝登录，不计爆破失败）；P11 任务同样只下发 IP 字面量，网关拒绝非 IP 的探活目标，并在自身拨号钩子里按内置名单再拦一次。
>   - **对供给方只给通用提示**：P1/轻检/一次性密码引导的连接失败一律为「管理端口不可达」，握手失败为「SSH 握手失败」，P11 失败为「经网关连接 host:port 失败(…)」；具体错误（解析地址、拒绝名单命中、底层错误串）只写 `slog`，避免探活成为探测内网的回显通道。
> - **预期主机指纹（CR-S1 Minor，推荐）**：供给方在机器上执行 `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`，把第二列（`SHA256:` + 43 位无填充 base64）作为 `expected_host_fingerprint` 在 ② 建节点或 ⑤ 填写连接信息时提交；格式不符 40001（不建节点/不保存连接信息）。提交即视为供给方带外确认：同一事务内钉死为已确认指纹（`host_key_confirmed_at=NOW()`），写审计 `node.host_key_preconfirmed`（`after.source=node_create|ssh_update`）。之后的首次连接——**含一次性密码引导**——在 SSH 握手的主机密钥回调里比对，不一致即中止：**密码不会发出**，节点转 `key_mismatch` 并记录实际观测指纹（同 P2 不一致处理：停止新分配、通知、审计 `node.key_mismatch`），返回 40900「…握手阶段已中止, 一次性密码未发送…」；供给方核对后经 ⑦ 确认实际指纹或改正连接信息。一致时首次完整探活直接通过 P2，无需 ⑦ 的 TOFU 确认步骤。
>   - **首次填写连接信息**（此前无 host）不算换机器：保留 ② 预置的指纹；此后改 host/port 照旧清除钉死。⑤ 提交的预期指纹覆盖当前指纹（含已确认值），旧值记入审计 `before`。
>   - **推荐路径 = 手动加公钥（④a）+ 预期指纹**：平台全程不接触密码，首次连接即校验指纹。不提供预期指纹时行为不变（TOFU：先连接、记录观测指纹、⑦ 确认），但此时一次性密码会在指纹确认之前发给首次握手到的主机——上架向导与 API 文档须提示这一点并推荐上述路径。
> - ⑤ 带一次性密码时：先保存连接信息再登录；登录或写公钥失败返回 40001「连接信息已保存, 但一次性密码登录安装公钥失败…」，连接信息保留，供给方可改走手动加公钥。
> - ⑥ 首次连接（指纹未确认）只执行 P1–P3：写一份 `fail` 探活报告（P2 详情含观测指纹与核对命令），节点回到 `unverified`，任务以 `succeeded` + `result.awaiting_host_key` 结束，并发站内信；此阶段不执行任何 nvidia-smi/docker 命令。⑦ 确认后自动入队完整探活。
> - 运营告警统一以 `slog.Error("运营告警: …")` 输出，由日志告警规则接收；本阶段不新增告警表。
> - 正式接口契约见 `docs/api/managed-rental-api.md`。

### 25.4.3 探活检查项

探活由 `node_tasks.kind=probe` 执行，结果写 `node_probe_reports`。

| # | 检查 | 方法 | 必检 | 不通过的后果 |
|---|------|------|:--:|------|
| P1 | TCP 可达 | 连接管理端口，3 次，超时 5s | ✅ | 不可上架 |
| P2 | SSH 握手与指纹 | x/crypto/ssh，钉死指纹比对 | ✅ | `key_mismatch` |
| P3 | 管理密钥认证 | 平台私钥登录 | ✅ | 不可上架 |
| P4 | GPU 清单 | `nvidia-smi --query-gpu=index,uuid,name,memory.total,pci.bus_id,driver_version --format=csv,noheader` | ✅ | — |
| P5 | 声明一致性 | 型号与 `gpu_catalog` 归一后比对商品 `gpu_model`；卡数 = 节点声明卡数；显存误差 ≤ 3% | ✅ | 不可上架，报告逐项列出差异 |
| P6 | 拓扑 | `nvidia-smi topo -m` 解析为 `topo_group`（NVLink/NVSwitch/同 PCIe 交换/同 NUMA） | ✅ | — |
| P7 | 健康 | ECC 不可纠正错误计数、退役页、近 24h 内核日志 Xid（读 `journalctl -k`；无权限则记为"未知"） | ✅ | 有 DBE/致命 Xid 的卡标 `faulty`，不计入可售 |
| P8 | 主机资源 | CPU 核数、内存、`df` 数据盘、OS、内核 | ✅ | 不足以按卡切分 → 不可上架 |
| P9 | 容器运行时 | `docker info`、`docker run --rm --gpus all <平台探针镜像> nvidia-smi -L` | ✅ | 不可托管 |
| P10 | 磁盘配额能力 | 探针容器带 `--storage-opt size=1G` 启动 | ⚠️ | 不可分卡，只能整机 |
| P11 | 租约端口：网关可达 | 在端口段内起临时 sshd 容器，经网关做一次自检登录 | ✅ | 不可上架（防火墙没放网关） |
| P12 | 租约端口：未裸露 | 同一临时端口，从主服务出口 IP 连接，**必须连不上** | ✅ | 不可上架（端口对公网开放） |
| P13 | 短压测 | 平台探针镜像内每卡 60s 矩阵乘：出现掉卡 / 致命 Xid / 功耗或温度降频 → 不通过；算力低于 `gpu_catalog` 该型号基准的 `fleet.probe.min_perf_ratio`（默认 0.7）→ 不通过 | ✅ | 该卡标 `faulty` 不计入可售；全部卡不通过则不可上架 |

P12 只能证明"主服务出口连不上"，不能证明对全网关闭；这是已知局限，上架规范 v2 中由供给方承诺，并在周期探活中复测。

P4–P8 的输出来自供给方宿主机，理论上可被篡改；P13 在平台镜像内实测算力，作为卡型与健康的独立证据，因此设为必检。`gpu_catalog` 未填写该型号基准时 P13 只校验稳定性、不比对算力，并在报告中注明。

平台对节点执行的命令为固定模板（参数只来自平台生成值和数据库，经白名单校验），不拼接任何用户输入，杜绝命令注入。

> **S1 实现口径（T-078，与上表差异）**
> - **P5**：显存误差 ≤ 3%；GDDR 卡开启 ECC 时可见显存少 1/16，先按该比例还原再比较。
> - **P5 型号归一（CR-S1）**：商品型号与 nvidia-smi 名称用同一规则归一——大写、按非字母数字切分，去掉品牌（NVIDIA/Tesla/GeForce/Quadro）、显存容量（`80G`/`80GB`）、显存类型（HBM2/2E/3/3E）与板卡形态（PCIe/SXM/SXM2–5）token，归一后的 token 序列**必须完全相同**。`D`/`Ti`/`S`/`NVL` 等后缀都区分型号：`RTX 4090-24G` 不匹配 `RTX 4090 D`，`V100-32G` 不匹配 `V100S`，`H100-80G` 不匹配 `H100 NVL`，这些机器须按其自身型号建商品。
> - **P7**：问题卡标 `faulty` 不计入可售；**只有全部卡都有问题才判 P7 不通过**（部分卡故障节点仍可上架，按健康卡数出售）。不可纠正 ECC、退役页/行重映射待生效或失败、近 24h 致命 Xid 计入问题卡。
> - **P9**：探针容器只挂空闲卡（`--gpus "device=<空闲卡>"`），校验容器内可见卡数；镜像为 `fleet.probe_image`（digest 固定，须含 python3 + CUDA 版 torch，P13 在其中执行）。
> - **P11**：不起临时 sshd，改为在探针镜像内起临时 TCP 监听（accept 后关闭，容器端口 8000），由访问网关的 `SelfTestPort(node, host, port)` 做连通自检。**网关（S2）未接入时 P11 一律判不通过**，因此 S1 单独上线时节点无法进入 `verified`（预期行为，不伪造通过）。
> - **P11/P12 端口**：在端口段内**从末尾向下**选宿主机未监听（`ss -Htln`）的端口，与开通分配（S2，从段首向上）错开；S1 尚无租约，不查 `port_claim`，S2 接入后需同时排除已分配端口；端口段须至少容纳「卡数 + 1」个端口。
> - **P13**：逐卡判定，出现降频、掉卡、压测后新增致命 Xid/ECC 或低于基准 × `min_perf_ratio` 的卡标 `faulty`；**全部卡不通过才判 P13 不通过**；无空闲卡（全部在租）时 P13 通过并在详情注明。
> - **结论落库**：全部必检项通过 → `verified` + `status=online`，同步卡槽（健康卡 `free`、问题卡 `faulty`，此前 `faulty` 的卡恢复健康后回 `free`），重算库存。任一必检项不通过 → `failed` **且 `status=offline`**（上表/25.4.4 写的是 `schedulable=0`；实现保留 `schedulable` 作为供给方排空开关，不被探活改写，改由 `failed`+`offline` 退出可售）。端口复测失败同样处理。例外：周期补跑的完整探活若只在 P1–P3 失败（连不上），只写报告，在线状态交给轻量探活判定。探活进行中 SSH 信息被修改或节点被停用 → 结论作废（`result.discarded=true`），不改节点状态。

### 25.4.4 周期探活

| 项 | 频率 | 作用 |
|----|------|------|
| SSH 轻量探活（P1-P4 + 容器状态 + `nvidia-smi` 利用率/温度/ECC/Xid） | 60s | 更新 `supplier_nodes.status`、`last_probe_ok_at`；写 `node_heartbeats`（沿用 docs/23 的表与 `products.health` 聚合口径） |
| 端口复测（P11、P12） | 24h，以及每次开通前 | 端口失守 → 停止新分配 + 通知 |
| 完整探活（P1–P13，含每卡短压测） | **每 12 小时（半日探活）**；供给方手动 / 运营触发 / 指纹变化后；开通前距上次完整探活超过 12h 先补跑 | 重新生成报告；任一必检项失败 → 节点 `schedulable=0` 停止新分配，在租租约按 25.7.6 计入停机 |

判定沿用 docs/23：连续失败 90s 视为 `offline`，`products.health` 由节点状态聚合，`offline` 阻断下单。托管节点（`mgmt_mode='ssh'`）的在线状态**只由 fleet 写**：scheduler 现有每 30s 的心跳超时清扫（`scheduler.Repository.MarkStaleOffline`）两条 SQL 均增加 `AND mgmt_mode<>'ssh'`，否则不推心跳的 SSH 节点会被反复打成离线、与 fleet 判定来回抖动。fleet 每轮 SSH 探活成功即写 `last_heartbeat_at` 与 `node_heartbeats`，`products.health` 聚合口径不变。

完整探活中的侵入项**不触碰在租资源**：P9 的探针容器只挂空闲卡（`--gpus device=<空闲卡 uuid>`，无空闲卡则以 `--gpus 0` 只验运行时）；P11/P12 只用未分配端口；P13 只压空闲卡。在租卡只做 P4/P7 只读检查，买家无感知。

卡级状态同步：P4/P7 发现某卡消失或出现致命错误 → 该卡 `gpu_slots.state=faulty`；若该卡在租 → 租约状态不变，写 `leases.resource_alert`（订单详情展示"资源异常"）并通知买家/供给方/运营，同时开始记录停机（25.7.6）。节点整体 `offline` 超过 5 分钟同样处理。

> **S1 实现口径（T-079，与上文差异）**
> - 轻量探活只覆盖 `verified` 且指纹已确认的节点：钉死指纹建连（P1–P3）+ `nvidia-smi` 利用率/温度/ECC（含 UUID，即 P4 只读部分）+ Docker 守护进程存活 + 近 2 分钟内核日志 Xid。**容器状态检查**（在租容器是否运行）随租约在 S2 实现。
> - 成功即写 `last_heartbeat_at`/`last_probe_ok_at`/`node_heartbeats` 与 `available_cards`；距上次成功超过 90s → `offline` + 通知供给方，恢复后自动 `online`。指纹变化 → `key_mismatch`。
> - **只对空闲卡**自动标 `faulty` 并通知供给方；在租卡掉卡/致命错误在 S1 只输出运营告警日志，`leases.resource_alert` 与停机记录属于 S2（T-082 起）。
> - `faulty` 卡的恢复只经完整探活（轻量探活不把 `faulty` 改回 `free`）。
> - 完整探活每 12h、端口复测每 24h 由调度循环自动入队；"开通前距上次完整探活超过 12h 先补跑"随开通流程在 S2 实现。

## 25.5 托管开通（付款后）

### 25.5.1 时序

```
支付确认 payment.confirmPayment (现有事务)
  └─ 订单 paid (compute)；LeaseHooks.OnPaidTx：租约 reserved→pending；卡槽 reserved 保持；入队 provision 任务
fleet worker 认领 provision (同节点串行)
  ├─ ⓪ 订单 paid→provisioning、租约 pending→provisioning（同一事务，守卫式）
  ├─ ① 复核：节点 online、指纹一致、卡槽仍归本租约
  ├─ ② 下发/校验 DOCKER-USER 链规则：租约端口段只放行网关 IP（幂等）
  ├─ ③ 校验基础镜像（接入探活时已预拉取，此处只校验 digest；缺失才拉取）
  ├─ ④ 创建数据卷 + 容器（规格见 25.5.2），生成容器 sshd 主机密钥，记录其指纹
  ├─ ⑤ 自检：主服务以系统自检身份经网关登录 → 执行 nvidia-smi -L → UUID 与分配一致
  └─ ⑥ 成功：订单 provisioning→active、lease_start=自检通过时刻、lease_end 按周期换算；
         生成交付记录与登录信息；通知买家
     失败：重试 ×3（指数退避）；仍失败 → 同商品其他节点重新分配一次；
         再失败 → 释放卡槽、租约 failed、订单 paid/provisioning→cancelled（lease_start_at 保持 NULL）、通知三方
                  → 由 payment 现有的 queueCancelledPaidRefunds 自动发起全额原路退款，不需运营操作、不新增退款路径
```

重新分配时卡槽与订单在同一事务内切换：原节点卡槽 `reserved→free`、新节点按 docs/26 §26.5.2 预留，租约 `node_id` 更新，失败则整体回滚并走"再失败"分支。

**付费成功即生效（Q-41 已定）**：托管订单没有签收环节，也不需要供给方任何操作；支付回调即触发开通，自检通过即可登录。基础镜像在接入时已预拉取，开通目标 P95 ≤ 2 分钟。开通期间订单为 `provisioning`，**开通耗时不计入买家租期**（租期从可登录时刻起算），自检结果即交付证据（写审计 + 可选上链，复用 REQ-H 存证钩子）。人工模式的签收流程不变。

### 25.5.2 租约容器规格

```
docker run -d --name omnis-l-<lease_no> \
  --label omnis.lease=<lease_no> \
  --gpus '"device=<uuid1>,<uuid2>"' \
  --cpus <C> --memory <M>g --memory-swap <M>g --pids-limit 8192 \
  --shm-size <min(M/2,64)>g \
  --storage-opt size=<disk_per_card_gb × k>G \
  -v omnis-l-<lease_no>-data:/root/workspace \
  --network omnis-l-<lease_no>-net \
  -p <租约端口>:22 \
  --restart no \
  <基础镜像@sha256:…>
```

| 规则 | 值 |
|------|----|
| CPU / 内存 | 先扣主机保留（默认 2 核 / 8 GB），剩余按 `k / 节点总卡数` 等比切分，向下取整 |
| 磁盘 | `disk_per_card_gb × k`；不支持配额的节点只能整机，不设上限但监控告警 |
| 禁止项 | `--privileged`、挂载 docker.sock、host 网络/PID/IPC、任意宿主目录挂载（模型缓存只读挂载除外，见 docs/27） |
| 重启策略 | `--restart no`：节点重启或离线恢复后，fleet 依次 ① 校验主机指纹 ② 下发 DOCKER-USER 规则 ③ 启动在租容器 ④ 经网关自检；任一步失败不启动容器，停机持续计入 25.7.6，直到自检通过 |
| 镜像 | 平台维护的基础镜像列表（配置项，按 digest 固定），v1.2 只提供平台镜像 |
| 容器内认证 | `authorized_keys` 只有网关上游公钥，带 `from="<网关出口IP>"`；禁用密码登录 |

多租户共享内核的风险：容器逃逸理论上可越权访问同机其他租约。缓解：禁止特权与宿主挂载、保持默认 seccomp/AppArmor、驱动与 Docker 版本纳入探活最低版本要求。该风险在使用规范 v2 中告知，并在 `docs/24` 风险表登记。

> **S2 实现口径（T-084，与 25.5.1/25.5.2 差异）**
> - **步骤 ⓪ 的放弃条件**：订单不在 `paid/provisioning`（已取消/退款/冻结）或租约不在 `pending/provisioning`、已改到别的节点 → 任务 `failed`（不重试、不进死信）。**冻结中的订单也放弃开通**：解冻（T-088）须为仍处于 `provisioning` 的租约重新入队 `provision`。其余一切节点/网络/网关问题均为可重试错误，耗尽后走 T-083 的换节点/退款。
> - **整机托管（`delivery_kind=bare_metal`）未接入**：下单预留时返回 50000「整机托管开通尚未接入(T-089), 暂不可下单」，已有的 bare_metal 租约 provision 任务直接 `failed`。
> - **② DOCKER-USER 规则**：管理账户只在 docker 组、无 sudo（25.4.1），规则借平台探针镜像以 `docker run --rm --network host --cap-drop ALL --cap-add NET_ADMIN --cap-add NET_RAW` 在宿主机网络命名空间内下发，**探针镜像须含 `iptables-nft` 和/或 `iptables-legacy`**。对每个存在 `DOCKER-USER` 链的后端分别处理：本端口段（`-m conntrack --ctorigdstport <start>:<end> --ctdir ORIGINAL`）的规则恰为"每个网关出口 IP 一条 `RETURN` + 其后一条 `DROP`"即视为已就位，否则删除本端口段全部旧规则后插回链首（不动供给方自己的规则与 Docker 默认 `RETURN`）。宿主机没有 `DOCKER-USER` 链 → 可重试失败，不建容器。**只支持 IPv4**：`accessgw.egress_ips` 含 IPv6 时开通失败并写明原因（ip6tables 未覆盖，IPv6 出口需另行设计）。已知风险：容器内 iptables 与宿主机 iptables 的 xtables 锁不共享、容器内 nft 版本须与宿主机内核兼容，须在真机上验收。
> - **③ 镜像**：S2 只使用 `fleet.base_images` 的第一项（买家选镜像属后续迭代）；本地不存在（`docker image inspect` 按 digest）才拉取，拉取上限 30 分钟。**基础镜像须含 `openssh-server`（`/usr/sbin/sshd`、`ssh-keygen`）与 `/bin/sh`**。
> - **④ 容器**：入口为 `/bin/sh -c '<base64 脚本>'`：写 `/root/.ssh/authorized_keys`（仅 `from="<网关出口IP,…>" <网关上游公钥>`，公钥按解析结果重新序列化、丢弃注释）、缺失时生成 ed25519 主机密钥、`exec sshd -D` 且只用 ed25519 主机密钥、禁用密码与键盘交互、`PermitRootLogin=prohibit-password`；**不加 `no-port-forwarding`**（买家需 `ssh -L`）。端口从端口段**开头**取第一个既未被本节点租约占用（`port_claim`）也未在监听的端口，与 `container_name/volume_name` 在同一守卫式 UPDATE 写入（`uk_node_port` 拦截并发）；重试沿用已占端口。建容器前 `docker rm -f` 同名半成品容器，网络/数据卷存在即复用（幂等）。不支持磁盘配额（P10）的节点只允许整机（`k = 总卡数`），不加 `--storage-opt`。容器主机指纹最多等 30s 读取，写入 `upstream_host_key_fp`。
> - **⑤ 自检**：经 `GatewaySelfTester.SelfTestLease`（T-085 accessgw 实现）以系统自检身份登录网关公网入口，`nvidia-smi -L` 的 UUID 集合必须**恰为**分配的卡；另从主服务出口对 `节点:租约端口` 做一次 TCP 连接，**连得上即失败**（端口未限制来源）。网关未接入（`Gateway=nil`）时自检明确失败，订单保持 `provisioning`，不写交付记录，耗尽后退款——不伪造通过。
> - **⑥ 激活**：同一事务内 订单 `provisioning→active`（交付记录 `delivered` + `selftest_passed_at`，`credential_encrypted` 只含网关入口 `accessgw.public_host:public_port` 与登录名，不含节点地址）、租约 `provisioning→active`（`access_until = orders.lease_end_at`、`provisioned_at`）、卡槽 `reserved→leased`（必须恰好迁移 `cards` 张）、清空 `resource_alert`；提交后通知买家「算力已开通」→ `/console/buyer/orders/<order_no>`。若自检期间订单被并发取消/冻结，`ActivateManagedOrderTx` 返回空，任务以 `abandoned=true` 成功结束，租约保持 `provisioning`，残留容器由 purge（取消路径）或解冻重开（T-088）处理。
> - **周期复核**：节点重启后的"重新下发规则 → 启动容器 → 自检"（25.5.2 重启策略）属 T-087；在此之前依赖 12h 完整探活与轻探活。轻探活发现在租/预留卡异常（掉卡、不可纠正 ECC、致命 Xid）写入对应租约 `leases.resource_alert`，恢复后清空；不迁移租约或卡槽状态，停机认定与补偿属 T-105。P11 端口自检从端口段末尾向下选，并跳过所有已被租约占用的端口（含容器停止时未监听的）。

- 认证方式（任选）：
  1. **公钥（推荐）**：买家在账户里维护公钥（`buyer_ssh_keys`，每人最多 10 把），对其名下所有托管租约生效，可随时增删。
  2. **密码**：复用 C-06 访问凭证——`access_key` 不变，`access_value` 作为网关登录密码，仍通过现有 `GET/POST /orders/:id/access-credential[/reveal]` 查看并留审计。网关只把密码转给主服务比对，自身不保存。
- 买家拿不到节点 IP、供给方账户和容器端口。

### 25.6.2 网关鉴权与路由

```
买家 ──SSH──► sshpiperd ──► omnis 插件
                              │ 1. 查本地缓存(≤30s, 只缓存"允许")
                              │ 2. 未命中: POST /internal/accessgw/auth
                              │      {login, method, pubkey_fp | password, remote_ip}
                              ▼
                         主服务: 校验登录名→租约; 租约 state=active 且 now < access_until;
                                 公钥属于租约买家 / 密码: 解密 access_value 后 subtle.ConstantTimeCompare;
                                 失败计数(Redis, 按 IP 与 登录名+IP)
                              │ ◄── {allow, upstream_host, upstream_port,
                              │      upstream_host_key_fp, access_until, cache_ttl_s}
                              ▼
               sshpiperd 用网关上游私钥登录容器 sshd(校验容器主机指纹), 双向透传
```

| 机制 | 规则 |
|------|------|
| 缓存 | 只缓存"允许"结果，TTL = min(30s, access_until − now)；"拒绝"不缓存 |
| 撤销推送 | 插件每 5s 拉 `GET /internal/accessgw/revocations?cursor=`，命中即清缓存 |
| 爆破防护 | 同一来源 IP 10 分钟内失败 20 次封 30 分钟（Redis 键 `accessgw:fail:ip:<ip>`）；同一「登录名 + 来源 IP」10 分钟失败 10 次锁 15 分钟（键 `accessgw:fail:login:<login>:<ip>`，仅锁密码方式，公钥不受影响）——不按登录名单独计数，避免他人故意输错把买家锁死；返回统一的"认证失败"，不区分登录名是否存在 |
| 主服务不可达 | 新连接一律拒绝（fail-closed）；已建立会话不受影响 |
| 内部接口保护 | 网关与主服务同 VPC，网关只走**内网**调用；主服务 nginx 新增一个仅监听内网地址的 server 块暴露 `/internal/accessgw/*`，公网 server 块对该前缀返回 404；firewalld 只对网关内网 IP 放行该端口：`firewall-cmd --permanent --add-rich-rule='rule family=ipv4 source address=<网关内网IP>/32 port port=<内部端口> protocol=tcp accept'` |
| 内部接口签名 | 请求头 `X-Gw-Timestamp`、`X-Gw-Nonce`（16 字节随机，hex）、`X-Gw-Signature` = HMAC-SHA256(`accessgw.hmac_secret`, `method\npath\nts\nnonce\nhex(sha256(body))`)；时间偏差 > 60s 拒绝；nonce 用 Redis `SET accessgw:nonce:<nonce> 1 NX EX 300` 去重，已存在即拒绝（防重放）；验签失败统一 40100 |
| 网关上游密钥 | 一把 ed25519，私钥只存在网关主机（文件 0400），**不进数据库**；公钥由 fleet 写入每个租约容器；轮换 = 先下发新公钥到所有在租容器再切换 |

### 25.6.3 会话审计

网关在会话开始/结束时批量上报 `POST /internal/accessgw/sessions`：登录名、来源 IP、认证方式、开始/结束时间、上下行字节数、断开原因。**不记录会话内容**。买家可在订单页查看自己租约的会话记录，运营可在后台按租约/IP 检索。保留 180 天。

> **S2 实现口径（T-085，与 25.6.2/25.6.3 差异）**
> - **组件**：网关 = sshpiperd **v1.6.1**（`github.com/tg123/sshpiper`，版本固定）+ 本仓库 gRPC 插件 `backend/cmd/accessgw`（基于 `libplugin`，只注册 publickey/password 认证与 VerifyHostKey、PipeStart/PipeError/PipeCreateError 回调；none 与 keyboard-interactive 不开放）。插件参数：`--main-url`/`ACCESSGW_MAIN_URL`（主服务内部接口 `http(s)://内网地址:端口`）、`--upstream-key-file`/`ACCESSGW_UPSTREAM_KEY_FILE`（网关上游 ed25519 私钥，权限必须 0400/0600，不支持口令保护）、`--upstream-user`（默认 `root`）；`accessgw.hmac_secret` 只从环境变量 `ACCESSGW_HMAC_SECRET` 读取（≥ 32 字节），不接受命令行参数。业务逻辑在 `backend/pkg/accessgw`（缓存、撤销、会话队列、P11 拨测），与 sshpiperd 解耦以便测试。
> - **v1.6.1 的 API 差异**：`Upstream.host/port` 已弃用，插件返回 `uri = tcp://host:port`（IPv6 带方括号）；上游主机密钥由插件的 VerifyHostKey 回调按本连接的 `upstream_host_key_fp` 比对（优先于 `known_hosts_data`），不符即拒绝建立管道。**插件拿不到字节计数**，`bytes_up/bytes_down` 恒为 0（字段保留）；**插件也无法主动切断已建立的管道**——撤销/到期只阻止新连接，已建立会话的到期断开须在容器侧完成（T-087，见 25.7.1 "断开现有会话"）。
> - **内部接口**：不是 nginx server 块，而是主服务进程内**独立的 `http.Server`**，只监听 `accessgw.internal_listen`（内网地址；公网 gin 路由不注册这些路径）。路径前缀 `/api/v1/internal/accessgw`：`POST /auth`、`GET /revocations?cursor=`、`POST /sessions`、**新增 `POST /probe-result`**（P11 回报）。请求体上限 1 MiB。
> - **签名**：签名串 `method\nuri\nts\nnonce\nhex(sha256(body))`，其中 `uri` 是 **RequestURI（路径 + 查询串）**，查询串受签名保护；签名为小写 hex。时间偏差 > 60s、nonce 非 32 位小写 hex、nonce 重放（Redis `SET accessgw:nonce:<nonce> NX EX 300`）、签名不符均返回 **40100**；Redis 不可用返回 **50000**（不跳过去重）；签名通过但路径未知返回 40400。
> - **鉴权判定**：登录名须为合法租约号；租约 `state=active`、`delivery_kind=container`、`now < access_until`、上游端口与主机指纹齐全才可能放行。公钥按指纹匹配租约买家**未吊销**的 `buyer_ssh_keys`；密码与 C-06 访问凭证（解密后）常量时间比较。`cache_ttl_s = min(30, access_until − now)`。
> - **爆破计数**：**只有密码失败计数**（公钥失败不计——SSH 客户端会依次尝试 agent 里的多把公钥，计数会误封正常买家）。来源 IP 按 `net.ParseIP` 规范化（同一 IPv6 不同写法共用一个键）。IP 键 10 分钟 20 次 → 封 30 分钟，**封禁期间该 IP 所有认证方式都拒绝**；登录名+IP 键 10 分钟 10 次 → 锁 15 分钟，**只锁密码方式**。系统自检身份不计数、不受封禁影响。任何 Redis 错误按失败处理（拒绝 + 50000）。
> - **系统自检身份**（`fleet.selftest_key_file` 公钥指纹，主服务启动时计算）：
>   - 只能登录 **`provisioning` 且已写入上游端口与主机指纹**的租约（开通步骤 ⑤）；响应 `system=true`、`cache_ttl_s=0`，网关不缓存、不上报会话。`active` 及其他状态的租约对系统身份一律拒绝，买家对 `provisioning` 租约也一律拒绝。
>   - **P11 端口自检**：主服务在 Redis 写一次性任务 `accessgw:probe:<token>`（`{host,port}`，2 分钟过期），以系统身份登录临时用户名 `p-<token>`；`/auth` 对系统身份 + 已登记 token 返回 `{allow:false, probe:{token,host,port}}`（其他身份或未登记 token 不下发任务）；网关从**自身出口**对 `host:port` 做 5s TCP 连接，`POST /probe-result` 回报（写 `accessgw:probe:<token>:result`，120s 过期；未登记 token 40400），然后拒绝该登录。主服务最多等 10s 读取结果，结束后删除两个键。
>   - 主服务连接网关公网入口时**固定网关主机密钥**（新增配置 `accessgw.host_key_fingerprint`），不符即失败——不会把冒充者的自检/探活结果当真。网关未配置、不可达、指纹不符、超时均使开通/P11 明确失败，不伪造通过。
> - **撤销游标**：格式 `"<unix 秒>-<lease id>"`；空游标返回 `{logins:[], cursor:"<now−2s>-0"}`（起点，不回放历史）。按 `(access_changed_at, id)` 严格递增返回，**只返回 2 秒之前的变化**（`access_changed_at` 为秒精度，避免同秒内未提交/较小 id 的行被跳过），每页最多 1000 条，无新行时游标不动；非法游标 40001。网关每 5s 轮询，单次最多翻 20 页；**轮询失败即清空整个放行缓存**（fail-closed）。撤销与鉴权交错时用纪元号防护：鉴权请求在途期间发生过撤销，则该次放行不入缓存。因此撤销生效上限 ≈ 5s 轮询 + 2s 滞后。
> - **会话上报**：网关在 PipeStart 入队开始事件、PipeError 入队结束事件（`end_reason`：`closed` 或错误摘要），每 5s 批量上报，失败保留重试；队列上限 20000，满了丢最旧的并计数。认证通过但未建立管道的连接表项 10 分钟后清理，不产生事件。主服务按 `gw_session_id` upsert：`ended_at/end_reason` 只写一次（COALESCE），字节数取较大值（GREATEST）；未知登录名、字段非法、系统自检指纹的事件计入 `ignored` 不报错；单批 > 500 条 40001。
> - **清理周期**：会话记录 180 天保留，清理由 fleet 周期任务**每小时**执行一次（25.11 写的是 1d）。

## 25.7 到期、宽限与清除

### 25.7.1 时间线

| 时点 | 动作 |
|------|------|
| 到期前 24h / 2h / 30min（不足的周期按比例取前两档） | 站内通知 + 短信（Issue #16 接通后）；容器内 `wall` 广播 |
| 到期 T | `compute` 到期任务将订单 `active→completed`（现有 `CompleteExpiredLeases`），同一事务：租约 `active→grace`、`access_changed_at=now`、卡槽 `leased→draining` |
| T + ≤5s | 网关拉到撤销，清缓存，新连接拒绝并提示"租期已结束，续租后恢复" |
| T + ≤60s | fleet 执行 `stop`：`docker stop -t 30`（已有会话随容器 sshd 退出而断开）；完成后卡槽 `draining→free`，库存归还 |
| 宽限期内 | 容器与数据卷保留；GPU 已释放可再售 |
| 宽限期满 | `purge`：删除容器、数据卷、租约网络、端口规则；写清除回执；租约 `purged` |

宽限期默认：时/日计费 24h，周/月计费 72h，包夜 24h（配置项）。**宽限期不收保管费**（Q-33 已定），订单费用一次结清。

托管租约的到期检查由 fleet 以 30s 周期执行（只处理 `fulfillment_mode=managed`），以满足 G4；主服务现有 5 分钟任务继续处理人工模式。两条路径都走 `releaseStock` 的守卫式状态流转，同一订单不会被处理两次。

**冻结或退款中的订单到期**：现有 `CompleteExpiredLeases` 只处理 `active` 订单，`frozen` / `refunding` 的托管订单到期后不会被它结束。托管侧**以租约为准**：fleet 到期任务按 `leases.access_until` 扫描，不看订单状态——到期即撤销访问、`docker stop`、卡槽 `→draining→free`，租约 `→grace`；冻结中（`suspended`）的租约到期同样停容器、释放卡，但租约保持 `suspended`、容器与数据卷保留作为核查现场，**不进入宽限清除计时**，运营结案后再进入 `grace`。订单状态不动，由运营结案（解冻→`completed` / 退款→`refunded`）时再流转；结案前订单不满足分账条件（25.7.6），资金留在待分账账户。

### 25.7.2 与续租衔接（沿用 order_renewals，不新增续租模式）

| 续租类型 | 托管模式下的履约 |
|---------|----------------|
| `extend`（到期前） | 支付事务内更新 `orders.lease_end_at` 与 `leases.access_until`；网关下次鉴权即生效；无需任何节点操作 |
| `restart`（到期后，宽限期内） | 在**原节点**预留 k 张空闲卡：原卡空闲 → `docker start` 原容器；原卡被占 → `docker commit` 后以新卡重建，挂载原数据卷。环境与数据完整保留。原节点无 k 张空卡 → 报价接口返回不可续，提示可新下单 |
| `restart`（宽限期后） | 按 docs/26 §26.5.2 在任一节点重新预留卡槽，新开容器，数据已清除 |

托管订单的 `restart` 续租**在下单（`pending_payment`）时即经 `LeaseHooks.RenewTx` 预留卡槽**，不调用 `DecrProductStock`；续租单关单超时则释放；`renewalQuoteTx` 的余量校验对托管订单改为查卡槽（宽限期内查原节点，宽限期后查商品全部节点）。

`restart` 支付成功后，原订单转 `paid` 并由 fleet 自动重新开通（替代"供给方重新交付 + 买家重新签收"），新租期以自检通过时刻起算。`docker commit` 产生的镜像在租约 `purged` 时一并删除。

### 25.7.3 冻结、退款、风控

| 事件 | 动作 |
|------|------|
| 运营冻结订单 / 风控冻结 | 租约 `suspended`；网关拒绝；节点侧 `docker exec` 结束容器内全部 sshd 会话；**不停容器**（保全现场供核查），GPU 仍占用 |
| 解冻 | 租约恢复 `active`；冻结因买家违规 → 不顺延；经核查为误冻结 → 冻结时长按 25.7.6 计入平台责任停机 |
| 退款完成（`CompleteRefund`） | 同到期处理，但宽限期为 0：立即停机并清除 |
| 疑似挖矿 | 每 5 分钟对在租容器执行 `docker top` 匹配平台维护的特征（矿工进程名、`stratum+tcp://` 参数），并读取容器网络命名空间的 `/proc/net/tcp{,6}` 比对矿池常用端口与平台维护的矿池地址清单（进程改名无法绕过外连特征）→ 生成风控告警（REQ-G-001）；命中 `stratum` 参数或矿池外连直接走冻结，其余仅告警待人工（Q-42） |

### 25.7.4 整机（bare_metal）托管

- 开通：平台在节点上创建账户 `omnis-l-<lease_no>`（加入 sudo），写入网关上游公钥；买家经网关登录该账户。
- 到期：网关拒绝 → 结束该账户全部进程 → 删除账户与家目录 → 节点 `verify_status=needs_reimage`，**停止再售**。
- 再售前：供给方重装系统并确认 → 平台走一次完整探活（指纹变化须供给方重新确认）→ 恢复 `verified`。
- 原因：买家持有 root，可留下任意后门或直接用机器公网 IP 绕开网关，平台无法单方面保证回收。该限制在上架规范 v2 与商品页明示。

### 25.7.5 清除回执

`purge` 完成后写 `audit_logs`（`action=lease.purged`），内容：租约号、节点、被删除的容器 ID / 卷名 / 网络名 / 端口规则、各步骤退出码、完成时间、执行者=系统。清除是**逻辑删除**（删除容器层与卷），不承诺介质级擦除；使用规范 v2 提示买家对敏感数据自行加密。回执哈希可走 REQ-H 存证钩子。

### 25.7.6 停机补偿与供给方约束（Q-37 已定）

原则：平台持续探活（60s 轻量 + 12h 完整），交付给买家的资源应当可用；**租期内因机器原因不可用，补偿买家时长或费用，由供给方承担**。

**停机认定**（写 `lease_outages`，一段停机一行，自动开始、自动结束）：

| 原因 `cause` | 开始 | 结束 | 责任方 |
|-------------|------|------|-------|
| `node_offline` | 节点判定 `offline`（连续 90s 探活失败） | 恢复 `online` 且租约自检通过 | 供给方 |
| `gpu_fault` | 租约内任一卡 `faulty` / 掉卡 / 致命 Xid | 卡恢复且自检通过 | 供给方 |
| `container_down` | 租约容器非买家原因退出（OOM 除外）且平台重启失败 | 重启成功 | 供给方 |
| `full_probe_failed` | 12h 完整探活影响在租卡的必检项失败 | 复测通过 | 供给方 |
| `night_unpark_failed` | 包夜窗口开始时卡被宿主机占用（docs/26 §26.6.4） | 开通成功；当晚未开通则整晚计入 | 供给方 |
| `provision_delay` | 仅包夜当晚订单（租期终点固定，开通耗时会吃掉租期，docs/26 §26.6.5）：支付成功时刻 | 自检通过；期间若命中上面任一供给方原因，该段改记对应原因 | 平台 |
| `gateway_down` | 网关不可用 | 恢复 | **平台**（平台承担，不扣供给方） |
| `wrong_freeze` | 误冻结，经运营核查确认 | 解冻 | 平台 |

累计停机 < `fleet.outage.min_minutes`（默认 5 分钟）的单段不计；同一时段多个原因只计一次。

**补偿方式**（买家在订单页二选一，未选择时默认顺延时长）：

| 方式 | 规则 |
|------|------|
| 顺延时长 | 停机结束时把租期顺延等长时间，同一事务内更新：`leases.access_until`、`orders.lease_end_at`、`order_deliveries.access_expires_at`（`requireRenewableAccess` 依赖它），以及该订单**待支付续租单**的 `lease_end_at` 与 `order_renewals.renewed_until`（否则 `ValidateRenewalPaymentTx` / `unusedRenewal` 要求的"续租起点 = 父订单租期终点"被打破，续租会被判冲突并自动退款）；顺延时段卡仍归本租约，供给方不得他用。包夜：补加一晚（同卡同窗口，若已被订则改为退费） |
| 退还费用 | 退款金额 = 订单实付 × 停机时长 ÷ 租期总时长（向下取整到分），在订单结算时一并处理 |

买家在订单页的停机记录中选择方式（`PUT /orders/:id/outage-remedy`，见 25.10），租期结束前可改；租期结束时未选择的按顺延处理已经发生，结束后剩余未补偿的停机一律按退费结算。

**由供给方承担的实现——分账时点（D-10）**：

托管订单不在开通时分账，改为**租期结束、停机结算完成后一次分账**。资金在此之前留在易宝待分账账户，补偿退款直接从待分账资金原路退回买家，供给方应结相应扣减，无需事后向供给方追款。

## 25.8 状态机

### 25.8.1 节点 `supplier_nodes.verify_status`

```
unverified ──verify──► verifying ──通过──► verified ◄──────────────┐
     ▲                    │                  │  │                  │
     │                    └──失败──► failed   │  └─指纹变化─► key_mismatch ──供给方确认+探活通过─┘
     │                                       ├─整机租约结束─► needs_reimage ──重装确认+探活通过──┘
     └──────────── 供给方修改 SSH 信息 ───────┤
                                             └─运营停用─► suspended ──运营恢复──► verified
```

`schedulable`（是否接受新分配）独立于上述状态：供给方"排空"节点时置 0，存量租约照常运行至到期。

> **S1 实现口径（T-077/T-081，与上图差异）**
> - **运营恢复**：`suspended ──运营恢复──► unverified`（自动入队完整探活，通过后才到 `verified`），不直接回到 `verified`。原因：停用时已释放空闲/停用/无租约故障卡槽与卡 UUID、指纹占用，必须重新核验。
> - **重装确认**：`needs_reimage ──重装确认──► verifying`，同时清除指纹钉死；新系统的首次连接会再走一次指纹确认（P1–P3 后回到 `unverified` 待确认）。
> - **发起探活**：`suspended`、`key_mismatch`（须先确认新指纹）、`needs_reimage`（须先重装确认）调用 verify 返回 40900。
> - **失败**：`failed` 同时置 `status=offline`；`failed` 可由供给方修复后再次 verify。
> - **节点代次（CR-S1 M4）**：`supplier_nodes.generation`（026 新增，`INT NOT NULL DEFAULT 0`）在 运营停用、运营恢复、重装确认、供给方修改 SSH 信息、确认主机指纹 时 +1；probe 任务 payload 携带入队时的 `generation`。代次不一致的探活：执行前直接中止（任务 `failed`，不连接节点、不写报告、不改节点状态）；执行中发生的变化在提交时作废（`markVerified/markFailed/markAwaitingFingerprint/markKeyMismatch/recordObservedFingerprint` 均带 `AND generation=?`，结果 `discarded=true`，不写报告）。停用/修改 SSH 信息同时把该节点**排队中与进行中**的 probe 任务置 `failed`（只作废 probe：存量租约的 stop/purge/kill_sessions 照常执行；provision 在执行时自查核验状态并走重试→死信换节点/退款，直接置 failed 会跳过善后）。
> - **到 `verified` 的唯一入口**：`markVerified` 只接受 `verifying`（本代次入队的完整探活）与 `verified`（周期补跑）。`failed`、`needs_reimage`、`key_mismatch`、`suspended`、`unverified` 都必须先经供给方/运营操作回到 `verifying`（发起探活 / 重装确认 / 确认新指纹 / 恢复后自动入队）。
> - **探活复用**：入队时只复用**同一代次**的未结束 probe；请求完整探活时只复用完整探活——`port_recheck` 不能代替完整探活（否则节点停在 `verifying` 却没有完整探活来结束它）。旧代次的排队任务与被完整探活取代的排队复检置 `failed`；在跑的复检保留，完整探活排在其后（同一节点串行）。确有完整探活任务后才把 `unverified/failed/key_mismatch/needs_reimage → verifying`。
> - **不会停在 `verifying`**：本代次完整探活因平台侧原因中止（缺管理密钥、`security.credential_key` 不可用、商品不存在等）或重试耗尽进死信时，若节点上已没有其他未结束的 probe，`verifying → failed` 并通知供给方"探活未能完成，请重新发起"（细节只在日志与任务 `last_error`）。
> - **运营重试死信探活**：按节点当前代次重写 payload，完整探活同时把节点置 `verifying`；节点为 `suspended/needs_reimage/key_mismatch` 或已有未结束的 probe 时 40900。

### 25.8.2 租约 `leases.state`

```
reserved ──支付──► pending ──认领──► provisioning ──自检通过──► active ──到期──► grace ──宽限满──► purging ──► purged
   │                                    │                       │ ▲   ▲  │                    │
   └─超时/取消─► cancelled               └─重试耗尽─► failed       │ │   │  └─restart续租─► pending (原节点恢复)
                                                                │ │   └─解冻── suspended ◄─冻结─┤
                                                     包夜窗口外 ─► parked ──窗口开始──┘           │
                                                                                     退款完成 ──► purging
```

所有状态迁移使用守卫式 `UPDATE … WHERE id=? AND state IN (…)`，`RowsAffected` 必须为 1，与订单状态迁移在同一事务内提交（订单侧沿用 `TransitionOrderStatusTx`）。

> **S2 实现口径（T-082，与上图差异）**
> - **新增迁移**：`pending ──取消/退款──► cancelled`（已付款未开通，尚无容器，卡槽 reserved→free，未领取的 provision 任务置 failed）；`provisioning ──取消/退款──► purging`（可能已建出部分容器，交 purge 清理）；`parked ──到期──► grace`（包夜租约在窗口外到期）。合法迁移全集见 `internal/fleet/lease.go` 的 `leaseFrom`，单测逐对覆盖。
> - **订单终态 → 租约**（`LeaseHooks.ReleaseTx`，订单守卫式迁移的同一事务内）：`reserved/pending`→`cancelled`；`provisioning`→`purging`+purge；`active/parked/suspended` 且订单 `completed`→`grace`（`grace_until`=时/日计费 `grace.short`、周/月计费 `grace.long`），卡槽→`draining`，入队 stop（优先级 1）；同上且订单 `cancelled/refunded`→`purging`（宽限 0），卡槽→`draining`，入队 purge（优先级 8）；其余状态幂等无操作。stop/purge 执行器属 T-087，接入前卡槽停在 `draining`，不计库存、不会被再分配。
> - **下单即建租约**：docs/25 §25.3 的钩子之外新增 `LeaseHooks.ReserveTx`：托管 `PlaceOrder` 在同一事务内写订单（`stock_reserved=0`、`fulfillment_mode=managed`，不扣 `products.stock`）→ 建租约（`reserved`）→ 按 docs/26 §26.5.2 预留同机 k 卡（k = 订单 `quantity`；`bare_metal` 要求整机全空闲且 k=总卡数）→ 重算派生库存。无整机余量返回 40900「所选卡数暂无整机余量」。`fleet.enabled=true` 但钩子未接入时下单返回 50000，不落库。
> - **锁顺序与派生库存（CR-S1 M3 修复）**：所有改卡槽的事务统一按 **订单 → 租约 → 节点行 → 卡槽 → 商品行** 加锁（下单预留在锁空闲卡前先锁节点行并复核可分配；周期探活标故障卡、订单终态释放卡槽同样先锁节点行），否则下单走 `idx_node_state` 二级索引、单卡停用走主键会交叉死锁（已用并发测试复现）。库存重算 `recomputeStockTx` 先 `SELECT id FROM products WHERE id=? FOR UPDATE`，再以**非锁定**计数写回；调用方事务必须是 **READ COMMITTED**（fleet `inTx` 与 compute 的托管下单/释放路径显式以 RC 开启，人工订单保持默认 RR），保证拿到商品行锁后的计数能看到前一个持锁者已提交的变更。未采用锁定计数（`FOR SHARE` 或 §26.5.4 的 `UPDATE … JOIN`）是因为它会在「已持有卡槽锁、正等商品锁」的事务上反向等锁形成死锁。`TestRecomputeStockSerializedByProductLock` 确定性复现丢更新（去掉商品锁时结果 15≠14）。
> - **托管续租**：T-088 接入 `LeaseHooks.RenewTx` 前，托管订单的续租报价/续租下单返回 50000「托管订单续租尚未接入」，不走人工续租路径。
> - **托管分账**：`settle_ready_at` 为空（租期末结算属 T-089）的托管订单（续租按根订单）一律不发起分账。

## 25.11 后台任务

| 任务 | 周期 | 位置 | 说明 |
|------|------|------|------|
| node_tasks worker | 常驻，`fleet.workers` 个协程 | fleet | 认领：`UPDATE … SET state='running', locked_until=NOW()+INTERVAL ? SECOND WHERE id=? AND state='pending'`，`RowsAffected=1` 才执行；同一节点同时只运行一个任务；锁过期视为崩溃，回到 pending；`attempts ≥ max_attempts` → `dead` + 运营告警 |
| SSH 周期探活 | 60s | fleet | 并发上限 `fleet.probe_concurrency` |
| 托管到期 / 宽限清除 | 30s | fleet | 按 `leases.access_until` 扫描；调 `compute` 暴露的到期方法（守卫式流转）后入队 stop/purge；写 `settle_ready_at`（25.7.6） |
| 停机认定与结算 | 60s（随探活） | fleet | 开/关 `lease_outages`；结束时按 `outage_remedy` 顺延或创建 `payment_refunds` |
| 到期提醒 | 5min | fleet | 通知去重键 `lease_no+档位` |
| 端口复测 | 24h | fleet | — |
| 挖矿特征扫描 | 5min | fleet | 见 25.7.3 |
| 会话记录清理 | 1d | fleet | 删除 180 天前记录 |

全部任务使用 `context` 超时（单条 SSH 命令默认 60s，拉镜像 30min），日志用 slog 并带 `trace_id`、`node_id`、`lease_no`。

> **S2 实现口径（T-083，与上表差异）**
> - worker 只认领**已注册执行器**的任务类型（当前 `probe`、`provision`；`stop/purge/kill_sessions` 执行器属 T-087，未接入前这些任务保持 `pending` 不被消耗、不进死信）。单条任务的执行 context 超时按类型取：`probe`/`provision` 均 44 分钟（覆盖拉镜像最坏 30 分钟）。**任务锁是短租约 + 心跳（CR-S1）**：认领时 `locked_until = NOW()+3min`，执行期间每 1 分钟以 `state='running' AND attempts=?` 守卫续期；续期命中 0 行（任务已被停用/改连接信息作废，或锁过期被回收后重新认领）立即取消本次执行；续期持续出错接近 3 分钟也取消，避免与回收后的重跑并发。worker 崩溃后锁 ≤ 3 分钟过期、由每分钟一次的回收转回 `pending`（按退避延后）或进死信，同一节点的后续任务（含重新发起的探活，复用该同代次任务）不再被孤儿 `running` 任务挡 45 分钟。
> - 可重试失败的退避：第 n 次失败后等待 `1min × 2^(n−1)`，上限 1h（默认 `max_attempts=3` 即 1min、2min 后重试，第 3 次失败进死信）。锁过期回收同样按退避延后，不立即重跑。
> - 不可重试失败（节点已删除/停用、payload 无法解析、租约已取消等）直接 `failed`，不重试、不进死信。
> - 进入死信只在"本次调用确实把任务转为 dead"时触发善后：被锁过期回收的 worker 迟到的失败回写不再触发（`retryLater` 以 `state='running' AND attempts=?` 加行锁判定），回收与 worker 不会对同一任务重复执行善后。
> - **provision 死信善后**（§25.5.1 "重试 ×3 → 换节点一次 → 再失败退款"）在单个 READ COMMITTED 事务内完成，锁顺序 订单 → 租约 → 节点行 → 卡槽 → 商品行，遇 MySQL 1213/1205 整体重试最多 3 次：
>   - 先校验订单仍为 `paid/provisioning`、租约仍为 `pending/provisioning` 且仍在死信任务所在节点，否则放弃（已被取消/退款/冻结，由 ReleaseTx 处理过）；
>   - 原节点卡槽：租约尚未开始建容器（`container_name` 为空）→ `free`；已开始建容器 → `draining` 并在原节点入队 `purge`（payload `cleanup_only=true` + `container_name/volume_name`，只清残留、释放本租约在该节点上的 draining 卡槽、**不迁移租约状态**，执行器属 T-087）。与上文"原节点卡槽 reserved→free"的差异即此：可能有半成品容器时不能直接放回。
>   - 首次耗尽（payload `reallocated=false`）：排除原节点按 docs/26 §26.5.2 重新预留；成功则租约 `provisioning/pending → pending`、`node_id` 更新、清空 `upstream_port/port_claim/upstream_host_key_fp/container_name/volume_name`，在新节点入队 `provision`（`reallocated=true`），订单保持 `provisioning`（不计租期），通知供给方；
>   - 再次耗尽或已无可用节点（40900）：订单 `paid/provisioning → cancelled`（`compute.FailManagedOrderTx`，吊销凭证，`lease_start_at` 保持 NULL）→ 由 `payment.queueCancelledPaidRefunds` 自动全额原路退款；租约 → `failed`（`fail_reason` 记最后错误）；通知买家（`/console/buyer/orders/<order_no>`）与供给方；slog `运营告警` 一条。
> - 新增租约迁移：`provisioning → pending`（换节点）、`pending → failed`（步骤 ⓪ 之前即失败且无节点可换）。
> - **probe 中止/死信（CR-S1 M4）**：完整探活因平台侧原因中止（不可重试的 `errProbeAborted`，代次不一致除外）或重试耗尽进死信（`onDead`），若节点仍为本代次 `verifying` 且没有其他未结束的 probe，则 `verifying → failed` + `status=offline` 并通知供给方。`port_recheck` 不改节点核验状态。
> - **运营重试 probe 死信（CR-S1 M4）**：按节点当前代次重写 payload（旧代次结论不会被代次守卫作废后白跑）；完整探活同时 `unverified/failed → verifying`。节点不存在、`suspended/needs_reimage/key_mismatch`（须先恢复/重装确认/确认指纹）或已有未结束的 probe 时 40900。
> - `POST /admin/node-tasks/:id/retry` 对 `provision` 死信返回 40900（死信已自动换节点或退款，重放会在已释放的卡槽上重复开通）。
