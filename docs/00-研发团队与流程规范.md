# 00 · 研发团队与流程规范

> 版本：v1.0 ｜ 日期：2026-07-13 ｜ 状态：待审查
> 本文档定义整个开发团队的**角色职责、工作流程、质量标准、文档规范**。所有团队成员必须遵守。

---

## 1. 团队组成与角色定义

### 1.1 角色矩阵

| 角色 | 代号 | 职责 | 产出物 | 禁止事项 |
|------|------|------|--------|----------|
| **需求分析师** | BA | 拆解需求为开发任务，澄清模糊点，维护需求-任务追溯矩阵 | 任务拆解表、验收标准 | 不直接写代码 |
| **架构师** | ARCH | 系统架构设计、模块边界、数据库设计、API 规范、技术选型 | 架构设计文档、DB ER 图、API 设计文档 | 不过度设计、不引入无必要复杂度 |
| **后端开发** | DEV | Go 代码实现、单元测试、数据流转测试、API 文档同步 | 可运行代码、单元测试、接口文档 | 不跳过测试、不绕过审查 |
| **测试工程师** | QA | 测试用例设计、单测覆盖检查、数据流转测试、回归测试 | 测试用例、测试报告、Bug 清单 | 不草率通过未达标模块 |
| **代码审查员** | CR | 所有文档和代码的最终质量把关 | 审查意见、批准/驳回标记 | 不放过重复文档、不遗漏逻辑缺陷 |
| **项目经理** | PM | 进度追踪、任务分配、里程碑管理、风险预警 | 任务看板、进度报告 | 不遗漏阻塞项 |

### 1.2 人员配置

| 角色 | 人数 | 说明 |
|------|:----:|------|
| BA | 1 | 可由同一个人兼任 BA + PM |
| ARCH | 1 | 可由同一个人兼任 ARCH + CR（但不能审自己的产出） |
| DEV | 1–2 | Go 后端主力 |
| QA | 1 | 可与 DEV 不同人 |
| CR | 1 | 必须与产出者不是同一角色 |
| PM | 1 | — |

> ⚠️ 关键约束：**同一人不能同时充当产出者和审查者**。架构师设计的文档由审查员审查，开发写的代码由测试+审查员双重把关。

## 2. 开发流程（阶段门禁制）

```
Phase 1: 需求任务拆解          Phase 2: 架构设计            Phase 3: 开发实现
┌──────────────┐  CR通过   ┌──────────────┐  CR通过   ┌──────────────┐
│ BA拆解任务    │────────→│ ARCH设计架构  │────────→│ DEV编码      │
│ 验收标准      │          │ DB/API/模块   │          │ QA测试       │
│ 依赖关系      │          │ 技术选型      │          │ CR审查       │
└──────────────┘          └──────────────┘          └──────┬───────┘
                                                           │
                                              ┌────────────▼──────────┐
                                              │ CR 审查通过 → PM 验收  │
                                              │ → 交付可运行项目       │
                                              └───────────────────────┘
```

### 门禁规则

| 阶段 | 入口条件 | 出口条件 | 阻塞后果 |
|------|----------|----------|----------|
| Phase 1 需求拆解 | 需求文档评审通过 | BA 产出任务表 + CR 审查通过 | 不得进入架构设计 |
| Phase 2 架构设计 | Phase 1 通过 | ARCH 产出架构文档 + DB ER + API 设计 + CR 审查通过 | 不得写一行代码 |
| Phase 3 开发实现 | Phase 2 通过 | DEV 代码 + QA 测试 + CR 审查全部通过 | 不得标记完成 |

## 3. TDD 开发规范

### 3.1 测试驱动流程

```
1. DEV 理解任务 → 写单元测试（红）→ 写代码让测试通过（绿）→ 重构（保持绿）
2. QA 运行全部单测 → 确认覆盖率和通过率达标
3. QA 编写数据流转测试（API 级别）→ 验证端到端数据正确性
4. CR 审查测试用例本身是否充分
```

### 3.2 测试要求

| 测试类型 | 最低覆盖率 | 负责 | 说明 |
|----------|:--------:|:----:|------|
| 单元测试 | ≥ 80%（核心模块） | DEV | service 层、业务逻辑层必测 |
| 数据流转测试 | 每个 API 至少 1 条 | QA + DEV | 从请求到响应的完整数据链路 |
| 集成测试 | 核心流程全覆盖 | QA | 下单→支付→分账 全链路 |
| 边界测试 | 每个模块至少 3 条 | QA | 空值/超长/并发/超时 |

### 3.3 测试工具
- 单测：Go 标准 `testing` + `testify`
- API 测试：`httptest` + 手写集成测试
- 数据验证：直接查询 MySQL/Redis 断言

## 4. 代码质量标准

### 4.1 Go 代码规范
- 遵循 Go 官方 `gofmt` / `go vet`
- 错误处理：严禁忽略 error，必须处理或显式 `_ =` 并注释原因
- 并发安全：共享状态必须用 `sync.Mutex` 或 channel
- Context 传递：所有可能超时的操作必须接受 `context.Context`
- 日志：结构化日志（`slog`），含 trace_id

### 4.2 架构约束（不过度设计）
| 约束 | 说明 |
|------|------|
| **不做微服务** | v1 单体应用，按包（package）做模块隔离，不引入服务网格/RPC |
| **不做 CQRS/Event Sourcing** | 简单 CRUD + 必要的异步队列（支付回调/区块链存证） |
| **不做自研框架** | 用标准库 + gin/echo 等成熟框架，忌自造轮子 |
| **不引入消息队列中间件** | v1 用 Redis list 做轻量队列（区块链存证异步化），不上 Kafka/RabbitMQ |

### 5.2 文档规则

- ❌ 禁止临时文档扔在根目录（必须归类到 docs/ 下）
- ✅ 所有文档尾部标注"审查状态 + 审查人 + 日期"
- ✅ API 文档与代码同步——DEV 改接口必须同步更新 `docs/api/` 下对应文件

## 6. 项目管理

### 6.1 任务状态
`待开始 → 进行中 → 待审查 → 审查中 → 已完成 / 打回重做`

### 6.2 任务跟踪
- 每个任务有唯一编号（如 `T-001`）
- 记录：负责人、估时、实际耗时、依赖、状态
- 每日同步：已完成 / 进行中 / 阻塞项

### 6.3 里程碑
| 里程碑 | 内容 | 出口 |
|--------|------|------|
| M0 团队+流程 | 本文档 + 审查通过 | — |
| M1 需求拆解 | 任务表 + 审查通过 | CR 批准 |
| M2 架构设计 | 架构 + DB + API 文档 + 审查通过 | CR 批准 |
| M3 账户与认证 | 注册/登录/KYC/RBAC | QA + CR 通过 |
| M4 算力撮合核心 | 挂牌/检索/下单/撮合/履约 | QA + CR 通过 |
| M5 支付分账 | 易宝对接/合单支付/分账/退款/对账 | QA + CR 通过 |
| M6 居间+金融+运营后台 | 居间/融资留资/审核/CRM/风控/配置 | QA + CR 通过 |
| M7 区块链存证 | BSN 对接/存证/验证 | QA + CR 通过 |
| M8 集成测试+交付 | 全链路测试/文档整理/部署 | PM 验收 |

## 7. 沟通规范

- **文档即沟通**：所有设计决策必须落在文档上，不允许"口口相传后代码里直接改了"
- **审查意见**：CR 审查通过前，不得进入下一阶段
- **阻塞上报**：任何阻塞超过 4 小时 → 立即通知 PM
