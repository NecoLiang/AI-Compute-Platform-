## 2. C-01：算力商品 4 种租赁范围类型

原设计只有"按卡分时/包月租赁"一种形态。现扩展为 4 类：

| 类型 | 代码值 | 说明 | 计费 | 交付物 |
|------|--------|------|------|--------|
| **零租** | `card_rental` | 按卡租用，短期灵活 | h / d / w | 卡的使用权（限期） |
| **零售** | `outright` | 买断，**使用权永久** | n（一次性） | 直接交付机器使用权 + 使用信息，信息在平台侧持续维护更新 |
| **成熟算力中心** | `center` | 整体打包（x 卡 / x 台 / 约 xxxP 算力） | d / w / m / n | 整柜或整机房交付 |
| **空心机房** | `colocation` | 已有机房但无设备，寻求设备入驻 | 议价 | 机柜位 + 电力 + 制冷 |

**关键字段扩展**：
```
product_type          零租/零售/算力中心/空心机房
machine_count         台数（算力中心用）
total_pflops_approx   总算力约 xxxP（算力中心用，纯文本，不做换算）
power_capacity        电力容量 MW（空心机房用）
```

> 注：`total_pflops_approx` 为供给方自行填报的**参考值**（如"约 128P"），平台**不做算力换算与校验**（已在需求评审中确认不做 GPU 算力换算表）。

## 4. C-05：算力中心资源同步与盘点

**业务背景**：算力中心的实际可售余量会因自用、其他渠道售出而变化，平台需要掌握真实余量。

**两种同步方式**：

| 方式 | 触发方 | 说明 |
|------|--------|------|
| **主动盘** | 平台 | 平台定期发起盘点请求，机房确认当前余量 |
| **被动报** | 机房 | 机房主动上报余量变化 |

**数据结构**：`resource_snapshots` 表记录每次盘点的 `stock_before` / `stock_after` / `sync_type` / `operator_id`，形成余量变更审计链。

**异常处理**：盘点结果与平台记录差异超过阈值 → 标记 `anomaly` → 触发风控告警。

**接口**：
```
GET  /supplier/resource-syncs           盘点记录列表
POST /supplier/resource-syncs/active    发起主动盘点
POST /supplier/resource-syncs/passive   机房被动上报
```

## 5. C-06：交付后访问权限管理

**业务背景**：算力中心开放机器的特定权限给买家，需要平台统一管理"谁能访问什么"。

**方案**：平台在交付环节生成一对访问凭证（`access_key` / `access_value`），买家持此凭证向算力中心发起请求，算力中心校验后放行。

```
供给方回填交付信息
      ↓
平台生成 access_key (ak-xxxx) + access_value (加密存储)
      ↓
买家确认签收 → 获得凭证
      ↓
买家持凭证请求算力中心 → 算力中心校验 → 放行特定权限
```

**凭证状态**：`待生成` → `已生成` → `已交付` → `已失效`（订单结束/退款后自动失效）

**安全要求**：
- `access_value` 数据库中 AES-256 加密存储（待接入 KMS）
- 前端脱敏展示，点击"查看完整"需二次确认并记审计日志
- 订单到期/退款/冻结 → 凭证自动失效

> ⚠️ 待确认（Q-24）：算力中心侧如何校验凭证？需要平台提供校验 API，还是采用标准协议（如 OIDC）？涉及与各机房的对接协议，需逐一沟通。

## 6. C-07：融资租赁增加中登网动产登记

**业务背景**：融资租赁业务中，租赁物需在**中国人民银行征信中心动产融资统一登记公示系统（中登网）**登记，查询登记状态是尽调必要环节。

**v1 实现范围**：
- 提供登记信息**查询与展示**（按企业名称/统一社会信用代码）
- 展示字段：登记编号、登记类型、登记期限、标的物描述、状态
- **数据来源**：v1 为人工录入/线下同步；后续可评估中登网数据接口对接

**合规声明**：页面需注明"登记数据来源于中国人民银行征信中心动产融资统一登记公示系统，仅供参考，以官方系统查询结果为准"。

## 7. C-08：设备商品发布（一手/二手）

**业务背景**：原设计中设备销售仅有"居间线索"形态，缺少设备商品的挂牌展示。

**新增能力**：设备厂商可发布设备商品，买家可浏览检索。

| 字段 | 说明 |
|------|------|
| `equipment_type` | GPU服务器 / 存储 / 网络 / 制冷 / UPS / 机柜 / 其他 |
| `condition` | **一手（new）/ 二手（used）** |
| `quantity` | 数量 |
| `unit_price` | 单价（分） |
| `region` | 所在地域 |

**与算力商品的关系**：算力市场页面用 tab 区分「算力商品」和「设备商品」，共用检索框架但字段不同。

**交易模式**：v1 设备商品为**询价撮合**（线索转化），不做在线支付下单——设备金额大、需线下验货议价。

### 10.4 本轮顺带修复的既存缺陷

实施过程中发现 5 个原有缺陷，均已修复：

| 严重度 | 缺陷 | 位置 | 后果 |
|:--:|------|------|------|
| **P0** | `PlaceOrder` 完全不校验 `Quantity` / `Duration` | `compute/service.go` | 传负数量 → 总价为负，且 `stock = stock - ?` 配 `stock >= ?` 判断会**凭空增加库存并通过校验**；传 `duration=0` → 总价 0 白嫖；超大值 → int64 溢出 |
| **P0** | `user_roles.role` ENUM 缺 `operator` / `admin` | `migrations/001:54` | 001 末尾种子语句整条中止（ERROR 1265 Data truncated），`user_roles` 表为空 → 种子管理员**没有任何角色**，`RBAC("operator","admin")` 保护的全部运营后台路由在全新部署上不可达 |
| P1 | `RenewOrder` 复用下单校验，会重复校验库存 | `compute/service.go` | 卡卖光后老客户**无法续租**（续租延长的是已持有的同一批卡，不应占用新库存）。已拆出 `ValidateRenewParams` |
| P2 | `switchMarketTab()` 被调用但从未定义 | `wireframe.html:208` | 点击导航「设备商品」抛 JS 错误 |
| P2 | 3 个弹框被 `openModal()` 引用但不在 `#modalOverlay` 内 | `wireframe.html` | `m-equip-inquiry` / `m-equip-order` / `m-finance-consult` 点击无反应——它们只定义在静态展示区，而 `openModal` 只在 overlay 内查找 |

> 另：按 C-08「v1 设备为询价撮合、不做在线支付」，已移除设备卡片的「立即采购」按钮与对应 `m-equip-order` 绑定。
