# 26 · 灵活计费与分卡租赁设计

> 版本：v1.2-draft ｜ 日期：2026-10-28 ｜ 状态：待审查 ｜ 产出：ARCH
> 对应变更：`docs/24` C-10（多计费方式 + 包夜）、C-11（分卡租赁）。范围决策、任务与开放问题见 `docs/24`。
> 依赖：`docs/25`（托管履约、`gpu_slots`、`leases`）。金额一律 int64 分，时间按 `Asia/Shanghai` 换算（docs/22）。

## 26.1 现状与目标

| 现状 | 问题 |
|------|------|
| 一个商品只有一个 `pricing_mode` + `unit_price` | 同一台机器不能同时按时/日/周/月卖 |
| `allowedPricingModes` 中零租只允许 h/d/w | 不能包月、不能包夜 |
| `available_hours` 是自由文本（如"22:00-08:00"） | 系统无法据此控制可用时段 |
| 零租 `quantity` = 卡数，从商品级库存池扣减（`CardsPerUnit=1`） | 不知道卡在哪台机器；买 4 卡可能落在 2+2 两台机器上，无法交付 |
| 订单不快照计费方式，读的是商品当前值 | 商品改计费方式后，存量订单的续租、到期换算会跟着变 |

目标：

1. 零租一个商品可同时开放 **小时 / 天 / 周 / 月** 中任意组合，各自定价。
2. 支持 **包夜**：只在夜间窗口可用，按晚计费。
3. 支持 **分卡**：一台多卡机按 1/2/4/6/8 卡切开出租，同一订单的卡**必须在同一台机器上**。
4. 订单快照计费方式，历史订单不受商品后续修改影响。

## 26.2 计费方式矩阵

| 商品类型 | 原允许 | v1.2 允许 | 说明 |
|---------|--------|----------|------|
| `card_rental` 全天可用 | h / d / w | **h / d / w / m**，可多选 | `monthly` 为新增 |
| `card_rental` 夜间窗口 | — | **nightly**（仅此一种） | 新增；**仅限托管模式**（需平台按时开停机） |
| `outright` / `center` / `colocation` | 不变 | 不变 | 本次不动 |

为什么全天商品与包夜商品分开、不允许同一商品既卖全天又卖包夜：一张卡若既可被"全天按周"租走，又可被"某几晚包夜"租走，两种占用的时间语义不同，会产生大量交叉冲突与碎片。按商品区分后，全天商品的卡用卡槽状态管理，包夜商品的卡用"卡 × 日期"日历管理，二者互不干扰。供给方若既想白天自用、夜里出租，就上架夜间窗口商品；若想 7×24 出租，就上架全天商品。

`duration` 语义不变（计费周期数）：`hourly`=小时、`daily`=天、`weekly`=周、`monthly`=月、`nightly`=**晚数**。

## 26.3 多价格

### 26.3.1 数据模型

新表 `product_prices`：每个商品每种计费方式一行，`unit_price` 为 **分 / 卡 / 周期**。

`products.pricing_mode` 与 `products.unit_price` 保留，作为**展示主价**（市场列表排序、筛选、现有前端字段），在保存价格的同一事务内同步为"已启用价格中周期最短的一项"。现有 `idx_search(gpu_model, region, pricing_mode, status)` 与市场筛选不需改动；市场新增"支持包月/包夜"筛选条件走 `product_prices` 子查询。

非 `card_rental` 商品不写 `product_prices`，继续使用 `products` 上的单价，读路径统一封装为 `PriceFor(product, mode)`：有价格行用价格行，否则回退到商品单价 —— 保证存量商品零迁移可用。

### 26.3.2 校验（`ValidateProductReq` 扩展）

| 规则 | 不满足 |
|------|-------|
| 至少启用一种计费方式；每种方式 `unit_price > 0`，`min_duration ≥ 1` | 40001 |
| 计费方式必须在 26.2 矩阵允许范围内 | 40001 |
| `nightly` 不能与其他方式并存；要求商品 `availability=night_window` 且 `fulfillment_mode=managed` | 40001 |
| `unit_price × 卡数上限 × 周期上限` 不溢出 `MaxOrderTotalFen` | 40001 |

**价格倒挂提醒**（只提醒，不阻断，返回 `data.warnings[]`，前端在发布页展示）：

| 提醒 | 条件 |
|------|------|
| 日价高于 24 小时价 | `daily > 24 × hourly` |
| 周价高于 7 天价 | `weekly > 7 × daily` |
| 月价高于 30 天价 | `monthly > 30 × daily`；未设日价时比较 `monthly > 4 × weekly` |

### 26.3.3 下单金额

`CalcOrderAmount(unitPriceFen, quantity, duration, feeRateBp)` 不变，`unitPriceFen` 改由 `PriceFor(product, req.PricingMode)` 取得；`quantity` 对零租仍是卡数。平台费率、费用快照沿用 Issue #3 已上线的口径。

## 26.4 租期换算

| 方式 | `lease_end_at` | 备注 |
|------|---------------|------|
| hourly / daily / weekly / monthly | 沿用 `LeaseEndAt(start, mode, n)`，日/周/月走日历 `AddDate` | monthly 已有实现（center 在用），零租直接复用 |
| nightly | 见 26.6.2 | 新增分支 |

`LeaseEndAt` 的 `default` 分支现按小时计算，必须为 `nightly` 显式加分支（窗口参数从订单快照读取），不能落入默认分支；`maxDurationByPricingMode` 增加 `nightly: 31`。`MaxDurationFor` 对未知方式回退最严格上限的行为不变。

起算点：人工模式仍为买家签收时刻；托管模式为自检通过时刻（`docs/25` §25.5.1）。

## 26.5 分卡租赁

### 26.5.1 规则

| 规则 | 说明 |
|------|------|
| 前提 | 托管模式 + `delivery_mode=container`。整机（bare_metal）和人工模式只能按整机卡数出租，不可分卡 |
| 可选卡数 | 供给方从平台允许集合中勾选，平台集合为配置项 `market.card_split_choices`，默认 `{1,2,4,6,8}`；所选值不得超过该商品下最大节点卡数 |
| 单订单单机 | 一个订单的 k 张卡必须分在同一节点；买家需要更多卡请下多单 |
| 定价 | v1.2 统一按"每卡单价 × 卡数"，不同卡数不单独定价（Q-34） |
| 资源切分 | CPU / 内存 / 磁盘按卡数等比切分，规则见 `docs/25` §25.5.2；商品页按"每卡配额"展示 |
| `min_order` | 托管分卡商品由可选卡数集合代替，`min_order` 不再参与校验 |

### 26.5.2 卡槽分配算法（下单事务内，确定性，无随机）

输入：商品 P、卡数 k（全天商品）。

```
1. 候选节点 = P 下 verify_status=verified 且 schedulable=1 且 status=online
              且 空闲卡槽数 ≥ k 的节点
2. 排序：(空闲数 − k) 升序      ← best-fit，优先填满碎片，保留大块给大单
         docs/23 稳定性得分 降序
         node_id 升序            ← 保证结果可复现
3. 取第一个节点 N：
     SELECT id, gpu_index, topo_group FROM gpu_slots
       WHERE node_id=N AND state='free' FOR UPDATE
     在 N 内选 k 张卡：
       a. 若某个 topo_group 的空闲卡数 ≥ k → 取空闲数最少且 ≥ k 的组，组内按 gpu_index 升序取 k 张
       b. 否则按组空闲数降序整组拼接，最后一组按 gpu_index 取足
     UPDATE gpu_slots SET state='reserved', lease_id=?, state_changed_at=NOW()
       WHERE id IN (…k 个…) AND state='free'
     RowsAffected 必须 = k；否则回滚本次尝试，换下一个候选节点
4. 最多尝试 3 个节点，仍失败 → 40900「所选卡数暂无整机余量」
```

同一事务内完成：订单写入、租约 `reserved` 写入、卡槽预留、商品派生库存重算。任何一步失败整体回滚。

拓扑优先的原因：多卡训练/推理的跨卡通信走 NVLink 或同一 PCIe 交换芯片时带宽高一个数量级；随机拿卡会让 2 卡租约落在跨 CPU 插槽的两张卡上，性能明显下降。

### 26.5.3 卡槽状态与订单的对应

| 订单事件 | 卡槽 |
|---------|------|
| 下单（`pending_payment`） | `free → reserved` |
| 关单超时 / 取消 | `reserved → free` |
| 开通成功（`active`） | `reserved → leased` |
| 到期 / 退款完成 | `leased → draining`；容器停止后 `draining → free` |
| 开通失败重新分配 | 原卡 `reserved → free`，新卡按 26.5.2 预留 |
| 卡故障 | 任意 → `faulty`（在租的同时触发 `docs/25` 资源异常处理） |
| 供给方停用单卡 | `free ↔ withheld` |

释放走 `releaseStock` 的守卫式流转，按订单 `fulfillment_mode` 分支：人工模式沿用 `stock_reserved` 归还；托管模式改为释放卡槽并重算派生库存。同一订单被关单任务、退款、运营改单并发命中时只会释放一次（docs/22 已有保证）。

### 26.5.4 派生库存

托管商品的 `products.stock` 不再由供给方手填，改为派生值，在任何卡槽状态变化的同一事务内重算：

```sql
UPDATE products p
JOIN (SELECT COUNT(*) AS free_cards, COALESCE(MAX(c),0) AS max_node FROM (
        SELECT COUNT(*) c FROM gpu_slots s JOIN supplier_nodes n ON n.id=s.node_id
        WHERE n.product_id=? AND n.verify_status='verified' AND n.schedulable=1
          AND n.status='online' AND s.state='free' GROUP BY s.node_id) t
     ) d
SET p.stock = d.free_cards,
    p.max_free_per_node = d.max_node,
    p.status = CASE
        WHEN d.free_cards = 0 AND p.status = 'active'   THEN 'sold_out'
        WHEN d.free_cards > 0 AND p.status = 'sold_out' THEN 'active'
        ELSE p.status END
WHERE p.id=? AND p.fulfillment_mode='managed';
```

售罄切换与人工商品 `DecrProductStock` 现有行为一致（只在 `active`↔`sold_out` 之间切换，不触碰 `draft/pending_review/offline` 等状态）。包夜商品的 `stock` 不以卡槽 `free` 计算，取"今天起 30 天内任一晚可订的最大卡数"，由夜间日历同一查询得出。

节点上下线（周期探活）也触发重算。`stock` 仅作展示与粗筛，**下单是否可行以 26.5.2 的卡槽预留结果为准**。市场列表新增"单机最多可租 `max_free_per_node` 卡"。

`ValidateProductReq` 对零租现要求 `Stock > 0`；托管商品豁免此项，提交的 `stock` 被忽略并以派生值覆盖。现有"上报库存"接口对托管商品返回 40001「托管商品库存由平台按卡槽自动计算」。

### 26.5.5 与 docs/23 调度建议的关系

`GET /supplier|admin/schedule-advice` 对托管商品改用 `gpu_slots` 计算容量与碎片，打分权重不变；人工商品沿用节点上报的 `available_cards`。

> **S3 实现口径（T-092/T-093，与 26.5 / 26.9 差异）**
> 1. **平台可选卡数集合是代码常量**：`compute.PlatformCardSplitChoices = {1,2,4,6,8}`，没有实现配置项 `market.card_split_choices`。要改集合须改代码，因为发布校验、默认值和下单校验必须同一来源，配置化留待有实际需求再做。
> 2. **`card_split_options` 上限按商品 `card_count`**：表示"单机卡数"，不按"商品下最大节点卡数"实时校验。节点接入晚于商品发布，发布时拿不到节点信息。超过节点实际卡数的选项由 availability / 下单返回「所选卡数暂无整机余量」兜底。省略时取集合中 ≤ `card_count` 的全部值。
> 3. **`max_free_per_node` 口径**：派生库存 SQL 的 `MAX(c)` 改为"单节点一次最多可租卡数"，与下单卡槽分配候选同一规则 `rentableOnNode`：节点有磁盘配额且非整机交付时取空闲卡数，否则只有整机全空闲才计整机卡数、否则计 0。`stock` 仍为全部空闲卡合计。
> 4. **列表 `min_cards` 各类商品口径**：托管 `max_free_per_node ≥ N`；人工零租用 `stock ≥ N`（人工商品无单机信息）；买断/算力中心用 `card_count ≥ N`（每份所含卡数）；空心机房无卡，不匹配。`pricing_mode` 筛选对有价格行的零租商品匹配任一已启用行，无价格行的存量商品与非零租商品回退 `products.pricing_mode`。
> 5. **availability 返回形态**：`quote` 额外带 `pricing_mode/quantity/duration`。`lease_preview` 增加 `start_rule`：托管为 `on_activation`（`start_at` = 查询时刻，`end_at` 按周期换算，仅为预估，D-6 以自检通过时刻为准）；人工为 `on_buyer_confirm`，签收时刻未知，`start_at/end_at` 为 `null`。`duration` 与下单同校验（须 ≥ `min_duration`），不提供默认值。包夜（S4 未接入）返回 `available=false`，`quote/lease_preview` 为 `null`。
> 6. **availability 可查询 `sold_out` 商品**：返回 `available=false`「商品已售罄」，不报 40400；`GET /products/:id` 对 `sold_out` 仍为 40400。只读检查，不做卡槽预留，与下单共用 `QuoteOrder` 和托管 `Feasible`（同一候选规则，只读查询，无锁）。
> 7. **限流失败即拒**：Redis 固定窗口，key `market:availability:rl:{user_id}`，每用户每分钟 30 次，超出 42900。Redis 未装配或不可用时返回 50000，不放开限流。
> 8. **调度建议的"可用"含本订单已占卡槽**：订单下单时卡槽已预留给它的租约，给本订单做建议时这些卡视为可用（`available_cards = free + own`）。否则已预留的节点会显示容量不足。响应新增 `capacity_source`（`heartbeat`/`gpu_slots`）和 `max_group_free`（同拓扑组最大可用，碎片指标）。托管节点不满足分配候选条件（未验收、暂停调度、非在线、无卡槽、整机/无配额规则）即 `unavailable`。
> 9. **释放只发生一次**：关单定时任务、买家取消、运营关单、退款完成都先锁订单行，再做带前置状态的守卫迁移。运营关单 `AdminUpdateOrderStatus(cancelled)` 由无条件写状态改为守卫迁移，输掉竞争的一方得 40900。托管订单走 `releaseLeaseTx`（按租约状态幂等，重算派生库存）。人工 `returnReservedStockTx` 遇托管订单直接报 50000，防误改 `products.stock`。并发测试见 `internal/fleet/release_race_integration_test.go`。
> 10. **未覆盖**：availability 不检查买家交易权限与角色（下单时仍检查），只检查交易总开关；托管续租（T-088）、整机托管（T-089）、包夜（S4）仍按原口径返回不可用。

## 26.6 包夜

### 26.6.1 夜间窗口

| 字段 | 规则 |
|------|------|
| `night_start_min` / `night_end_min` | 当天分钟数（0–1439），30 分钟对齐；默认 1320 / 480（22:00–08:00） |
| 跨零点 | `end ≤ start` 表示次日结束 |
| 窗口长度 | 4–14 小时 |
| 时区 | `Asia/Shanghai`，商品页明示 |
| `available_hours` | 保留为展示文本，夜间窗口商品由系统按窗口自动生成，不再接受自由输入 |

"某晚" 以**窗口开始的日期**标识（`night_date`）：10-28 晚 = 10-28 22:00 至 10-29 08:00。

### 26.6.2 租期

```
lease_start_at = night_start_date + night_start_min
lease_end_at   = (night_start_date + nights − 1 天) + night_end_min（跨零点再 +1 天）
```

租期内只有窗口时段可登录；窗口外租约为 `parked`（容器停止、数据保留、GPU 归还供给方）。

### 26.6.3 预订与防重

新表 `night_bookings(slot_id, night_date, lease_id)`，`UNIQUE(slot_id, night_date)` —— **由数据库唯一约束保证同一张卡同一晚不会被订两次**。

下单事务：

```
1. 候选节点按 26.5.2 同样的排序，空闲判定改为：
   该卡在 [night_start_date, night_start_date+nights) 内每晚都无预订，且卡槽非 faulty/withheld
2. 对节点 N 的卡槽行 SELECT … FOR UPDATE（串行化同节点并发下单）
3. 选 k 张卡（同样拓扑优先），批量 INSERT k × nights 行预订
4. 唯一键冲突 → 回滚本次尝试换下一节点；3 次失败 → 40900
```

同一订单所有晚使用**同一组卡**，这样容器可以跨晚复用、数据不丢。

| 事件 | 预订行 |
|------|-------|
| 关单 / 取消 | 删除该租约全部预订 |
| 退款完成 | 删除尚未开始的晚；已开始的晚保留作为履约记录 |
| `extend` 续租 | 在同一组卡上追加后续晚的预订；任一晚被占 → 40900「原卡位后续夜晚已被预订」 |
| 宽限期内 `restart` 续租 | 优先原节点原卡；原卡被占则同节点他卡（容器 commit 后重建，见 `docs/25` §25.7.2） |

### 26.6.4 每晚开停机

| 时点 | 动作 |
|------|------|
| 窗口开始前 10 分钟 | 检查本晚分配的卡上**无宿主机进程**（`nvidia-smi --query-compute-apps=gpu_uuid,pid`） |
| 窗口开始 | `unpark`：启动容器 → 自检 → 租约 `parked→active`、`access_until=本晚窗口结束` |
| 卡被占用 | 每分钟重试，最多 10 分钟；仍被占 → 本晚开通失败，通知买家与运营，按 `docs/25` §25.7.6 记供给方责任停机（`night_unpark_failed`）并扣信用分（T-023） |
| 窗口结束前 30 / 10 分钟 | 站内通知 + 容器内 `wall` 广播，提醒保存检查点 |
| 窗口结束 | `park`：网关拒绝新连接 → `docker stop -t 30` → 租约 `active→parked` |
| 最后一晚结束 | 走到期流程（`docs/25` §25.7），宽限期 `fleet.grace.nightly` |

单晚开通失败、晚间停机的补偿按 `docs/25` §25.7.6：默认补加一晚（同卡同窗口），无法补加则按晚退费，由供给方承担。

### 26.6.5 当晚预订

窗口开始后仍可预订当晚，截止为窗口开始后 2 小时，按整晚计价（Q-36）。当晚订单支付后立即开通，租期起点为实际开通时刻，终点不变。按 D-6「开通耗时不计入租期」：支付成功到自检通过超过 `fleet.outage.min_minutes` 的部分记为平台责任停机（`docs/25` §25.7.6 `provision_delay`），买家可选补一晚或按比例退费；买家在窗口开始后才下单而错过的时间不补偿（下单页明示）。

非当晚的包夜订单，首晚在窗口开始前 10 分钟预开通，窗口开始即可登录。

> **S4 实现口径（T-094/T-095，与 26.6 差异与补充；待业务方确认项标「假设」）**
> - **夜晚标识**：`night_date` = 窗口开始那天的上海日期；跨零点窗口 11-03 晚 = 11-03 22:00 ~ 11-04 06:00。窗口须 30 分钟对齐、时长 4-14 小时。
> - **可订范围（假设）**：起始夜晚 ≤ 今天起第 30 天，末晚 ≤ 今天起第 60 天；单笔 ≤ 31 晚。包夜只开放给夜间窗口 + 托管 + 分卡容器商品（Q-44），整机（bare_metal）包夜 40001。
> - **预订**：下单只写 `night_bookings`（不动卡槽），同一订单所有晚同一组卡；并发防重靠 `(slot_id, night_date)` 唯一键 + 锁节点行/卡槽行，冲突 40900。卡槽仅在每晚开窗时 `free→reserved→leased`，关窗 `→draining→free`。夜间窗口商品的节点只服务包夜租约。派生库存取可订范围前 30 晚中未预订卡合计最多的一晚（快照在重算时刻，假设）。
> - **`access_until` 口径（与上表差异）**：`leases.access_until` = 整单末晚窗口结束（不是"本晚窗口结束"）；每晚是否可登录由网关按订单窗口快照判定（[窗口开始, min(窗口结束, access_until))），提前开通的几分钟不放行（假设）。
> - **开窗**：在 窗口开始−10min 认领卡并检查宿主机 GPU 进程后立即 `docker start`（不等到窗口开始），占用重试至 应开通时刻+10min（应开通时刻 = max(窗口开始, 支付时刻)）。上一晚停容器任务未完成时本轮不开窗。关窗由 `stop` 任务 `docker stop`，网关同时拒绝新连接。
> - **首晚认领失败**：到 应开通时刻+10min 仍认领不到卡 → 整单开通失败全额退款（不换节点：包夜卡已按晚预订，假设）。
> - **补偿**：每个受影响的晚补加一晚（同一晚多段只补一晚）；补加晚的同一组卡已被预订 → 转退费。某晚从未尝试开通即过窗口按 `provision_delay`（平台）计（假设）。
> - **结算**：租期末一次分账（D-10），与其他托管订单相同：最后一晚到期进宽限/清除、停机补偿全部落地后写 `settle_ready_at`。
> - **未做**：包夜续租（仍 50000）；供给方修改已有预订商品的夜间窗口不校验与现有预订冲突（订单用快照，节点窗口实际按新值，可能冲突，假设由运营管控）。真实宿主机 `nvidia-smi --query-compute-apps`、`docker start/stop`、`wall` 广播行为**未验收**。

## 26.7 下单、续租、退款的改动点

| 位置 | 改动 |
|------|------|
| `PlaceOrderReq` | 新增 `pricing_mode`（零租多价格商品必填；省略时取商品展示主价方式，兼容旧前端）、`night_start_date`（包夜必填，`YYYY-MM-DD`，今天起 30 天内） |
| `validateOrderParams` | 增加：`pricing_mode` 已启用；`duration ≥ min_duration`；托管分卡商品的 `quantity ∈ card_split_options`；包夜 `duration ≤ 31` 且所有晚在日历开放范围内 |
| `PlaceOrder` | 托管商品：不调 `DecrProductStock`，改为 26.5.2 / 26.6.3 预留；人工商品：不变 |
| `orders` | 新增 `pricing_mode`、`night_start_date` 及夜间窗口快照（`night_start_min/night_end_min`）；存量订单的 `pricing_mode` 由 028 在迁移时回填（见下方「S3 实现口径 (CR M1)」），代码不再回退商品当前方式。`fulfillment_mode` 已在 026 加入（`docs/25` §25.9） |
| 续租报价 | 价格取 `PriceFor(product, 原订单 pricing_mode)`；该方式已被停用 → 不可续租（40900，提示新下单）；`order_renewals.pricing_mode` 已是快照，沿用 |
| 退款 / 关单 / 到期 | 按 26.5.3、26.6.3 释放卡槽与预订 |
| `allowedPricingModes` | 零租改为 `{hourly,daily,weekly,monthly,nightly}`，再叠加 26.3.2 的组合约束 |

**S3 实现口径 (CR M1)：存量订单计费方式快照在 028 迁移时回填，取代原"存量订单为 NULL、读取时回退、不回填"。**

- 原口径的问题：读取时回退的是**读取那一刻**的商品 `pricing_mode`。v1.2 起展示主价同步为已启用价格中周期最短的一项，商品重提后会漂移。例：日租商品有一笔已付款待交付的 3 天订单，供给方下架、加上小时价重提并审核通过后展示主价变成 `hourly`，该订单交付时租期只有 3 **小时**，续租也按小时价报价。
- 新口径：028 在给 `orders` 加列后立即回填，先取续租子订单自己的 `order_renewals.pricing_mode`（021 起已是快照，v1.2 前重新交付就按它换算），其余订单取迁移时商品的 `pricing_mode`：
  ```sql
  UPDATE orders o JOIN order_renewals r ON r.order_id=o.id SET o.pricing_mode=r.pricing_mode WHERE o.pricing_mode IS NULL;
  UPDATE orders o JOIN products p ON p.id=o.product_id SET o.pricing_mode=p.pricing_mode WHERE o.pricing_mode IS NULL;
  ```
  迁移时刻的值是可证明的：v1.2 前每个商品只有一种计费方式，旧代码对订单一律按商品当前方式换算租期与报价，028 本身不修改 `products` 行，所以回填值就是这些订单在 v1.2 前实际生效的方式；事后读取则无法证明。若商品在 v1.2 前已改过计费方式，旧代码当时就已按新方式处理其订单，回填冻结的也是这一既有行为，不做追溯更正。
- 代码只认订单快照：`OrderPricingMode` 遇 NULL/空串返回 `50000`「订单缺少计费方式快照…请联系平台核对」，交付、签收、续租报价均拒绝；订单列表、详情、供给方订单列表、可开票订单列表只输出快照，不再 `COALESCE` 商品方式（缺失时为空串，详情 `can_renew=false`）。
- 商品已不存在的订单（`orders.product_id` 无外键）无法回填，保持 NULL，按上一条报 `50000`；028 执行后须核对 `SELECT COUNT(*) FROM orders WHERE pricing_mode IS NULL` = 0，非 0 逐笔上报。
- **审批**：存量订单回填属于对生产业务数据的写入，须由业务负责人在 028 生产授权中一并批准（见 §26.11 第 3 条），未批准不得执行 028。

### 028_flexible_pricing.up.sql

```sql
ALTER TABLE products
    MODIFY COLUMN pricing_mode ENUM('hourly','daily','weekly','monthly','perpetual','nightly') NOT NULL
        COMMENT '展示主价方式; card_rental 的完整价格见 product_prices',
    ADD COLUMN availability ENUM('fulltime','night_window') NOT NULL DEFAULT 'fulltime' AFTER available_hours,
    ADD COLUMN night_start_min SMALLINT NULL COMMENT '0-1439, Asia/Shanghai' AFTER availability,
    ADD COLUMN night_end_min SMALLINT NULL AFTER night_start_min,
    ADD COLUMN card_split_options VARCHAR(32) NULL COMMENT '如 "1,2,4,8"; 仅托管 container 商品' AFTER min_order,
    ADD COLUMN max_free_per_node INT NULL COMMENT '派生值, 单机最多可租卡数' AFTER stock;

CREATE TABLE product_prices (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    product_id BIGINT NOT NULL,
    pricing_mode ENUM('hourly','daily','weekly','monthly','nightly') NOT NULL,
    unit_price BIGINT NOT NULL COMMENT '分/卡/周期',
    min_duration INT NOT NULL DEFAULT 1,
    enabled TINYINT NOT NULL DEFAULT 1,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_product_mode (product_id, pricing_mode),
    INDEX idx_mode_enabled (pricing_mode, enabled)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 存量零租商品: 以其当前计费方式/单价/最小时长生成一行价格(当前状态可证明, 允许回填)
-- 不按计费方式过滤: 001 曾允许零租使用 monthly, 存量 monthly 零租商品同样回填
INSERT INTO product_prices (product_id, pricing_mode, unit_price, min_duration, enabled)
SELECT id, pricing_mode, unit_price, GREATEST(COALESCE(min_duration,1),1), 1
FROM products
WHERE product_type='card_rental' AND pricing_mode IN ('hourly','daily','weekly','monthly');

ALTER TABLE orders
    ADD COLUMN pricing_mode VARCHAR(20) NULL COMMENT '下单时计费方式快照; 存量订单由 028 按迁移时商品方式回填' AFTER duration,
    ADD COLUMN night_start_date DATE NULL AFTER pricing_mode,
    ADD COLUMN night_start_min SMALLINT NULL AFTER night_start_date,
    ADD COLUMN night_end_min SMALLINT NULL AFTER night_start_min;

-- 存量订单快照回填 (S3 实现口径 (CR M1), 见 §26.7)
UPDATE orders o JOIN order_renewals r ON r.order_id=o.id SET o.pricing_mode=r.pricing_mode WHERE o.pricing_mode IS NULL;
UPDATE orders o JOIN products p ON p.id=o.product_id SET o.pricing_mode=p.pricing_mode WHERE o.pricing_mode IS NULL;
```
